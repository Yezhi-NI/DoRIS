# Модель Document

**Проект:** DoRIS
**Версия:** 0.1 beta
**Связанные модули:** `DR_DocumentFactory`, `DR_DocumentProcessor`

---

# 1. Назначение

`Document` — универсальная внутренняя модель документа DoRIS.

Она представляет результат распознавания в форме, независимой от конкретного OCR-провайдера и, насколько это возможно, от конкретной конфигурации 1С.

Общий поток данных:

```text
OCR API
   │
   ▼
OCR Provider
   │
   ▼
РезультатOCR
   │
   ▼
промежуточная модель OCR
   │
   ▼
DR_DocumentProcessor
   │
   ▼
Document
   │
   ▼
клиент DoRIS / объект 1С
```

Промежуточная модель OCR описана отдельно в `OCR_MODEL.md`.

`Document` находится на следующем уровне: это уже нормализованное представление документа, предназначенное для использования клиентским кодом.

---

# 2. Основной принцип

OCR-провайдер отвечает за получение и первичный разбор результата OCR.

`DR_DocumentProcessor` преобразует этот результат в `Document`.

`DR_DocumentFactory` определяет структуру `Document` и создает необходимые объекты данных.

Разделение ответственности:

```text
OCR Provider
     │
     │ provider-specific данные
     ▼
РезультатOCR
     │
     ▼
DR_DocumentProcessor
     │
     │ нормализация
     ▼
Document
     │
     ▼
DR_DocumentFactory / клиентский код
```

OCR-провайдер не должен создавать `Document`.

---

# 3. Создание Document

Базовая структура создается функцией:

```bsl
DR_DocumentFactory.СоздатьСтруктуруДокумент()
```

Функция возвращает структуру следующего вида:

```text
Document
├── ТипОбъекта
├── ТипДокумента
├── МассивСтрок
├── РеквизитыДокумента
└── ТабличнаяЧасть
```

`РеквизитыДокумента` создаются отдельной функцией:

```bsl
СоздатьРеквизитыДокумента()
```

а `ТабличнаяЧасть`:

```bsl
СоздатьТабличнуюЧастьДокумента()
```

Таким образом структура `Document` создается централизованно в `DR_DocumentFactory`.

---

# 4. Структура верхнего уровня

В версии 0.1 beta `Document` содержит пять полей.

| Поле                 | Назначение                                               |
| -------------------- | -------------------------------------------------------- |
| `ТипОбъекта`         | Тип объекта, который представляет распознанный результат |
| `ТипДокумента`       | Логический тип распознанного документа                   |
| `МассивСтрок`        | Текстовые строки документа, полученные из OCR            |
| `РеквизитыДокумента` | Реквизиты шапки документа                                |
| `ТабличнаяЧасть`     | Нормализованные строки товарной таблицы                  |

Базовая структура:

```text
Document
│
├── ТипОбъекта = ""
├── ТипДокумента = ""
├── МассивСтрок
│
├── РеквизитыДокумента
│
└── ТабличнаяЧасть
```

После создания `ТипОбъекта` и `ТипДокумента` не содержат заранее установленного значения.

Их заполнение относится к этапу обработки распознанных данных.

---

# 5. ТипОбъекта

`ТипОбъекта` определяет логический вид объекта.

В текущем рабочем потоке используется:

```text
Документ
```

`DR_DocumentProcessor` при обработке OCR-результата устанавливает:

```bsl
Документ.ТипОбъекта = "Документ";
```

Текущая структура фабрики при этом спроектирована так, чтобы в дальнейшем можно было использовать ее не только для документов, но и для других объектов.

На этапе 0.1 beta основной поддерживаемый сценарий — документ.

---

# 6. ТипДокумента

`ТипДокумента` предназначен для хранения логического типа распознанного документа.

В коде предусмотрены значения:

```text
Поступление
Реализация
```

Для определения типа предусмотрена логика распознавания таких текстовых вариантов, как:

```text
поступление товаров
поступление тмз
реализация товаров
реализация тмз
приходная накладная
расходная накладная
```

После определения типа устанавливается:

```text
Поступление
```

или:

```text
Реализация
```

При этом в основном рабочем pipeline версии 0.1 beta автоматическое определение `ТипДокумента` по `МассивСтрок` пока не вызывается.

Поэтому поле присутствует в модели, но может оставаться пустым.

---

# 7. МассивСтрок

`МассивСтрок` содержит обычные текстовые строки документа, полученные из промежуточной OCR-модели.

Источник:

```text
ДокументOCR.СтрокиДокумента
```

При обработке выполняется присваивание:

```bsl
Документ.МассивСтрок = ДокументOCR.СтрокиДокумента;
```

Пример:

```text
МассивСтрок
[
    "ТОО Поставщик",
    "Накладная № 125 от 15.09.2026",
    "Покупатель: ТОО Компания",
    "Итого: 8500"
]
```

На текущем этапе эти строки сохраняются в `Document`, но основной pipeline еще не выполняет полный автоматический разбор шапки документа на их основе.

`МассивСтрок` позволяет не терять распознанную текстовую информацию и использовать ее при дальнейшем развитии обработки реквизитов.

---

# 8. РеквизитыДокумента

`РеквизитыДокумента` является вложенной структурой.

Текущий состав:

```text
РеквизитыДокумента
├── Контрагент
├── Организация
├── ДатаДокумента
├── НомерДокумента
├── Валюта
├── СуммаДокумента
└── Комментарий
```

Начальные значения:

| Поле             | Начальное значение |
| ---------------- | ------------------ |
| `Контрагент`     | `""`               |
| `Организация`    | `""`               |
| `ДатаДокумента`  | `Неопределено`     |
| `НомерДокумента` | `""`               |
| `Валюта`         | `""`               |
| `СуммаДокумента` | `0`                |
| `Комментарий`    | `""`               |

Структура создается:

```bsl
DR_DocumentFactory.СоздатьРеквизитыДокумента()
```

---

# 9. Контрагент и Организация

В модели существуют два отдельных поля:

```text
Контрагент
Организация
```

Это позволяет интерпретировать стороны документа с учетом его направления.

Например, предусмотренная логика обработки различает:

```text
Поступление
    Поставщик → Контрагент
    Покупатель → Организация

Реализация
    Поставщик → Организация
    Покупатель → Контрагент
```

Это важно, поскольку слова `поставщик` и `покупатель` сами по себе не определяют, какое поле объекта 1С необходимо заполнять — это зависит от типа документа.

В версии 0.1 beta соответствующая логика присутствует в `DR_DocumentProcessor`, но еще не подключена к основному потоку обработки `МассивСтрок`.

---

# 10. ДатаДокумента

`ДатаДокумента` предназначена для даты исходного документа.

Начальное значение:

```text
Неопределено
```

В `DR_DocumentProcessor` предусмотрена обработка текстового представления даты, включая русские названия месяцев:

```text
января
февраля
марта
...
декабря
```

После преобразования строка может быть передана стандартным функциям преобразования строки в дату.

Эта логика подготовлена для обработки реквизитов документа, но в текущем основном pipeline пока не используется.

---

# 11. НомерДокумента

`НомерДокумента` предназначен для номера исходного документа.

Начальное значение:

```text
""
```

В `DR_DocumentProcessor` предусмотрено извлечение номера из строки вида:

```text
Накладная № 125 от 15.09.2026
```

с использованием символа:

```text
№
```

и маркера:

```text
от
```

Как и обработка даты, эта логика существует в модуле, но пока не является частью основного рабочего потока версии 0.1 beta.

---

# 12. Валюта

`Валюта` содержит распознанное обозначение валюты документа.

Начальное значение:

```text
""
```

Поле входит в универсальную структуру `Document`, но специальная логика преобразования или поиска объекта справочника валют в текущем рабочем pipeline отсутствует.

---

# 13. СуммаДокумента

`СуммаДокумента` предназначена для общей суммы документа.

Начальное значение:

```text
0
```

В таблице соответствий реквизитов предусмотрены варианты:

```text
сумма
итого
всего
```

которые сопоставляются с:

```text
СуммаДокумента
```

При обработке числового реквизита предусмотрено преобразование строкового значения в число.

В текущем основном pipeline разбор `МассивСтрок` на реквизиты еще не выполняется.

---

# 14. Комментарий

`Комментарий` предназначен для дополнительной текстовой информации документа.

Начальное значение:

```text
""
```

Предусмотрены соответствия:

```text
комментарий
примечание
```

к полю:

```text
Комментарий
```

---

# 15. Соответствие имен реквизитов

`DR_DocumentFactory` содержит таблицу соответствий между текстовыми именами реквизитов и полями `Document`.

Примеры:

```text
контрагент       → Контрагент
поставщик        → Контрагент
покупатель       → Контрагент

организация      → Организация

дата             → ДатаДокумента
документ дата    → ДатаДокумента
дата документа   → ДатаДокумента

номер            → НомерДокумента
номер документа  → НомерДокумента

валюта           → Валюта

сумма            → СуммаДокумента
итого            → СуммаДокумента
всего            → СуммаДокумента

комментарий      → Комментарий
примечание       → Комментарий
```

Эти соответствия централизованы в:

```bsl
DR_DocumentFactory.СоответствиеРеквизитовДокумента()
```

Это позволяет не размещать набор известных названий полей непосредственно в алгоритмах обработки.

---

# 16. ТабличнаяЧасть

`ТабличнаяЧасть` содержит нормализованные товарные строки распознанного документа.

В отличие от промежуточной OCR-модели, где таблицы представлены вложенными массивами физических ячеек, в `Document` используется стандартная:

```bsl
ТаблицаЗначений
```

Она создается:

```bsl
DR_DocumentFactory.СоздатьТабличнуюЧастьДокумента()
```

Таким образом:

```text
ТаблицыТоваров OCR
        │
        │ массивы физических ячеек
        ▼
DR_DocumentProcessor
        │
        │ нормализация
        ▼
Document.ТабличнаяЧасть
        │
        │ ТаблицаЗначений
        ▼
клиентский код
```

---

# 17. Колонки ТабличнойЧасти

В версии 0.1 beta фабрика создает следующие колонки:

```text
НомерСтроки
Номенклатура
ЕИ
Количество
Цена
СуммаБезНДС
СуммаНДС
Сумма
GTIN
NTIN
СтавкаНДС
Артикул
Код
```

Для некоторых колонок внутреннее имя и отображаемое имя отличаются.

В частности:

```text
ЕИ     → ЕдиницаИзмерения
Сумма  → СуммаСНДС
```

Следует различать фактическое имя колонки `ТаблицаЗначений` и ее заголовок.

---

# 18. НомерСтроки

`НомерСтроки` предназначен для номера товарной строки исходного документа.

Пример OCR-заголовка:

```text
№
```

сопоставляется с:

```text
НомерСтроки
```

---

# 19. Номенклатура

`Номенклатура` содержит распознанное наименование товара.

OCR-заголовок:

```text
Товар
```

сопоставляется с:

```text
Номенклатура
```

На уровне `Document` это распознанное значение.

Само по себе наличие текста в `Номенклатура` не означает, что соответствующий элемент справочника 1С уже найден.

Поиск объекта конкретной конфигурации относится к следующему уровню обработки.

---

# 20. Единица измерения

Для единицы измерения в `ТабличнаяЧасть` используется колонка:

```text
ЕИ
```

с заголовком:

```text
ЕдиницаИзмерения
```

При обработке некоторых OCR-таблиц единица измерения может находиться внутри значения количества:

```text
10 шт
```

В этом случае `DR_DocumentProcessor` умеет рассматривать `Количество` как расширяемую логическую колонку и разделять числовую и строковую части.

Подробный алгоритм описан в `TABLE_PROCESSING.md`.

---

# 21. Количество

`Количество` содержит количество товара.

В промежуточной OCR-модели оно может выглядеть как:

```text
"10"
```

или:

```text
"10 шт"
```

После нормализации `DR_DocumentProcessor` преобразует значение количества в число.

Таким образом в итоговой `ТабличнаяЧасть` количество уже не обязательно сохраняет исходный строковый тип OCR.

---

# 22. Цена

`Цена` содержит цену товарной позиции.

При заполнении итоговой табличной части `DR_DocumentProcessor` преобразует заполненное значение в число.

Если значение отсутствует:

```text
Цена = 0
```

---

# 23. СуммаБезНДС

`СуммаБезНДС` предназначена для суммы товарной строки без НДС.

При наличии значения оно преобразуется в число.

Если OCR не предоставил значение:

```text
СуммаБезНДС = 0
```

---

# 24. СуммаНДС

`СуммаНДС` содержит сумму НДС товарной строки.

При заполнении `Document` значение преобразуется в число.

При отсутствии значения:

```text
СуммаНДС = 0
```

---

# 25. Сумма

`Сумма` — фактическое имя колонки `ТаблицаЗначений`, предназначенной для суммы строки с НДС.

При создании таблицы ее заголовок задается как:

```text
СуммаСНДС
```

То есть:

```text
Имя колонки:      Сумма
Заголовок:        СуммаСНДС
```

Это различие важно учитывать при обращении к данным из кода.

---

# 26. GTIN и NTIN

В табличной части предусмотрены:

```text
GTIN
NTIN
```

Они предназначены для идентификаторов товара, если соответствующие значения присутствуют в распознанном документе.

В текущей версии DoRIS эти поля сохраняются в модели, но универсальная логика поиска номенклатуры по ним в основном pipeline отсутствует.

---

# 27. СтавкаНДС

В итоговой таблице предусмотрена колонка:

```text
СтавкаНДС
```

Она отличается от:

```text
СуммаНДС
```

`СтавкаНДС` описывает ставку налога, тогда как `СуммаНДС` — рассчитанную или распознанную сумму налога.

Следует учитывать, что таблица соответствий OCR-заголовков в текущей версии еще использует соответствие:

```text
НДС → НДС
```

тогда как фабрика итоговой `ТаблицаЗначений` создает колонку `СтавкаНДС`.

Это текущее различие реализации необходимо учитывать при дальнейшем развитии модели.

---

# 28. Артикул

`Артикул` предназначен для артикула товарной позиции.

OCR-заголовок:

```text
Артикул
```

сопоставляется с одноименным полем.

---

# 29. Код

`Код` предназначен для кода товара, присутствующего в исходном документе.

OCR-заголовок:

```text
Код
```

сопоставляется с:

```text
Код
```

`Код` является отдельным полем и не должен автоматически трактоваться как `GTIN`, `NTIN` или внутренний код справочника конкретной конфигурации.

---

# 30. Соответствие колонок OCR и Document

`DR_DocumentFactory` содержит соответствия известных заголовков OCR.

Основные соответствия:

```text
№                  → НомерСтроки
Код                → Код
Артикул            → Артикул
Товар              → Номенклатура
Количество         → Количество
ЕдиницаИзмерения   → ЕдиницаИзмерения
Цена               → Цена
Сумма              → Сумма
GTIN               → GTIN
NTIN               → NTIN
НДС                → НДС
СуммаНДС           → СуммаНДС
СуммаСНДС          → СуммаСНДС
```

Если распознанный заголовок отсутствует в таблице соответствий, `DR_DocumentProcessor` не отбрасывает колонку.

Для нее создается техническое имя:

```text
Колонка1
Колонка2
...
```

при этом исходное распознанное имя используется как заголовок колонки.

Это позволяет не терять неизвестные данные только потому, что DoRIS еще не знает их семантического назначения.

---

# 31. Преобразование OCR-таблицы в Document

Общий процесс:

```text
ДокументOCR.ТаблицыТоваров
          │
          ▼
СоздатьСхемуКолонок()
          │
          ▼
ОпределитьВариантСхемыТаблицы()
          │
          ▼
РазобратьСтрокуПоСхеме()
          │
          ▼
СоздатьТаблицуТоваров()
          │
          ▼
ЗаполнитьТабличнуюЧасть()
          │
          ▼
Document.ТабличнаяЧасть
```

Подробности определения физических и логических колонок вынесены в `TABLE_PROCESSING.md`.

---

# 32. Неизвестные колонки

DoRIS не требует, чтобы каждая колонка OCR-таблицы заранее присутствовала в модели.

Если известного соответствия нет, создается колонка вида:

```text
Колонка1
```

с исходным OCR-наименованием в качестве заголовка.

Например, если OCR вернул:

```text
Склад
```

и такого соответствия нет, результат концептуально будет выглядеть как:

```text
Имя:       КолонкаN
Заголовок: Склад
```

Это позволяет сохранить информацию и не связывать успешность распознавания с фиксированным набором колонок.

---

# 33. Document и объект конфигурации 1С

`Document` не является объектом метаданных 1С.

То есть:

```text
Document
```

не равен:

```text
ДокументОбъект.ПоступлениеТоваровУслуг
```

или любому другому конкретному объекту конфигурации.

`Document` — промежуточная прикладная модель DoRIS:

```text
OCR
 │
 ▼
Document
 │
 ▼
адаптация к конфигурации
 │
 ▼
объект 1С
```

Это разделение позволяет использовать результат распознавания независимо от того, какой документ и какая конфигурация будут использовать его дальше.

---

# 34. Создание объекта 1С

В `DR_DocumentFactory` присутствует функция:

```bsl
СоздатьДокумент(Документ, ОбъектЗаполнения)
```

Текущая реализация умеет передать `Document` в заполнение существующего объекта и заполнить его товарную табличную часть.

При этом используется:

```text
ОбъектЗаполнения.ПолучитьОбъект()
```

и строки:

```text
Document.ТабличнаяЧасть
```

переносятся в:

```text
ДокОбъект.Товары
```

Это уже не универсальная часть модели `Document`, а интеграционный уровень с конкретной конфигурацией 1С.

---

# 35. Поиск номенклатуры

При заполнении объекта 1С текущая реализация может искать элемент справочника:

```text
Номенклатура
```

по наименованию.

Если элемент найден, в строку документа устанавливаются:

```text
Номенклатура
СтавкаНДС
ЕдиницаИзмерения
```

из найденного элемента.

Это поведение относится к заполнению конкретного объекта 1С и не является частью структуры `Document`.

Сам `Document` может содержать только распознанное текстовое наименование товара.

---

# 36. Расчет НДС при заполнении объекта

При создании объекта 1С текущая реализация использует функции конфигурации для расчета суммы НДС.

Следовательно, необходимо различать:

```text
Document
    ↓
универсальные распознанные данные
```

и:

```text
объект 1С
    ↓
бизнес-логика конкретной конфигурации
```

Расчет налогов, заполнение счетов учета и запись документа не должны рассматриваться как свойства универсальной модели `Document`.

---

# 37. Зависимость заполнения от конфигурации

Текущий код заполнения объекта использует объекты и функции конкретной конфигурации, включая:

```text
Документы.ПоступлениеТоваровУслуг
Справочник.Номенклатура
Справочник.Контрагенты
Справочник.КлассификаторЕдиницИзмерения
```

а также функции учета НДС и заполнения счетов учета.

Поэтому эта часть `DR_DocumentFactory` не является полностью конфигурационно-независимой.

Универсальной следует считать прежде всего структуру:

```text
Document
```

и этап ее формирования.

Автоматическое создание и заполнение реального документа 1С требует адаптации к используемой конфигурации.

---

# 38. Результат DR_DocumentProcessor

После успешной обработки `DR_DocumentProcessor` возвращает структуру:

```text
Результат
├── Document
├── Markdown
├── JSON
└── Ошибка
```

При успешной обработке:

```text
Document = сформированный Document
Markdown = ""
JSON     = исходный итоговый JSON OCR-провайдера
Ошибка   = ""
```

Таким образом основной результат обработки — поле:

```text
Document
```

`JSON` сохраняется для диагностики и отладки.

Поле `Markdown` в текущем результате существует, но заполняется пустой строкой.

---

# 39. Результат при ошибке

При ошибке `DR_DocumentProcessor` возвращает ту же структуру результата:

```text
Document = Неопределено
Markdown = ""
JSON     = ""
Ошибка   = "<описание ошибки>"
```

Это позволяет клиентскому коду использовать одинаковую форму результата независимо от успешности обработки.

---

# 40. Пример Document

Концептуальный пример заполненной структуры:

```text
Document

ТипОбъекта:
    "Документ"

ТипДокумента:
    ""

МассивСтрок:
    [
        "ТОО Поставщик",
        "Накладная № 125 от 15.09.2026"
    ]

РеквизитыДокумента:
    Контрагент: ""
    Организация: ""
    ДатаДокумента: Неопределено
    НомерДокумента: ""
    Валюта: ""
    СуммаДокумента: 0
    Комментарий: ""

ТабличнаяЧасть:

    НомерСтроки | Номенклатура | Количество | ЕИ  | Цена | Сумма
    ----------------------------------------------------------------
    1           | Товар A      | 10         | шт  | 500  | 5000
    2           | Товар B      | 5          | шт  | 700  | 3500
```

Этот пример отражает текущий этап проекта: товарная таблица уже нормализуется, а реквизиты шапки документа могут оставаться незаполненными.

---

# 41. Что уже обрабатывается в 0.1 beta

В текущем основном потоке реализовано:

```text
OCR
 ↓
МассивДокументов
 ↓
СтрокиДокумента → Document.МассивСтрок
 ↓
ТаблицыТоваров
 ↓
нормализация физических и логических колонок
 ↓
ТаблицаЗначений
 ↓
Document.ТабличнаяЧасть
```

Также выполняется преобразование ряда числовых значений табличной части.

---

# 42. Что подготовлено, но еще не включено в основной поток

В `DR_DocumentProcessor` уже присутствуют функции для:

```text
определения типа документа
определения реквизитов
заполнения реквизитов
извлечения даты
извлечения номера документа
преобразования текстовых дат
```

Однако в текущем основном вызове `РазобратьДокументOCR()` эта логика не используется.

Основной поток сейчас выполняет:

```text
ТипОбъекта = "Документ"
        ↓
РазобратьТаблицыТоваров()
        ↓
ЗаполнитьТабличнуюЧасть()
```

Поэтому документация версии 0.1 beta не должна представлять автоматическое заполнение шапки документа как завершенную возможность.

---

# 43. Document как публичная модель данных

`Document` следует рассматривать как основной полезный результат распознавания DoRIS.

OCR JSON является данными внешнего сервиса.

Промежуточная OCR-модель является внутренним контрактом между провайдером и Processor.

`Document` является нормализованной моделью для дальнейшего использования.

```text
provider JSON
     │
     ▼
РезультатOCR
     │
     ▼
ДокументOCR
     │
     ▼
════════════════════
     Document
════════════════════
     │
     ▼
клиент DoRIS
```

Клиентскому коду не требуется знать внутреннюю структуру ответа PaddleOCR или Mistral OCR.

---

# 44. Граница универсальности

Основной архитектурный инвариант:

> `Document` не должен зависеть от формата ответа конкретного OCR-провайдера.

Второй инвариант:

> Структура `Document` должна описывать распознанный документ, а не конкретный объект метаданных конкретной конфигурации 1С.

Поэтому такие операции, как:

```text
поиск ссылки Номенклатура
поиск Контрагента
заполнение счетов учета
расчет НДС средствами конфигурации
запись документа
```

относятся к интеграции с 1С, а не к самой модели `Document`.

---

# 45. Расширение модели

При добавлении нового поля следует определить, относится ли оно к универсальному описанию распознанного документа.

Если да, оно может быть добавлено в:

```text
РеквизитыДокумента
```

или:

```text
ТабличнаяЧасть
```

Если поле имеет смысл только для конкретной конфигурации 1С, предпочтительно обрабатывать его на интеграционном уровне, не добавляя зависимость в универсальную модель.

Пример универсального поля:

```text
НомерДокумента
GTIN
Артикул
```

Пример потенциально конфигурационно-зависимого поля:

```text
СчетУчета
Субконто
СкладОрдер
```

Такие поля не следует автоматически включать в `Document` только потому, что они существуют в одной конфигурации.

# 47. Стабильность модели в версии 0.1 beta

В версии 0.1 beta структура `Document` еще может изменяться по мере развития распознавания реквизитов и поддержки новых типов документов.

При изменении модели необходимо учитывать:

```text
DR_DocumentFactory
        │
        ▼
структура Document
        │
        ▼
DR_DocumentProcessor
        │
        ▼
клиентский код
```

Изменения структуры `Document` являются более существенными, чем изменения внутреннего формата отдельного OCR-провайдера, поскольку `Document` используется за пределами provider-specific слоя.

Поэтому новые поля следует добавлять только тогда, когда они действительно относятся к универсальной модели распознанного документа.

# 48. Основной контракт Document

Для версии 0.1 beta базовый контракт можно представить следующим образом:

```text

├── ТипДокумента
│
├── МассивСтрок
│

│   ├── Контрагент
│   ├── Организация
│   ├── ДатаДокумента
│   ├── НомерДокумента
│   ├── Валюта
│   ├── СуммаДокумента

    ├── НомерСтроки
```
