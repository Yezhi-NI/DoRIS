# Обработка товарных таблиц в DR_DocumentProcessor

**Проект:** DoRIS
**Версия:** 0.1 beta
**Модуль:** `DR_DocumentProcessor`
**Область:** `Таблицы`

---

# 1. Назначение

Область `Таблицы` модуля `DR_DocumentProcessor` отвечает за преобразование таблиц, полученных от OCR-провайдера, в нормализованную товарную таблицу DoRIS.

OCR-провайдер передает таблицы в составе промежуточной модели OCR:

```text
ДокументOCR
├── СтрокиДокумента
└── ТаблицыТоваров
```

`ТаблицыТоваров` содержит массив распознанных таблиц.

Каждая таблица представляет собой массив строк, а каждая строка — массив физических ячеек OCR:

```text
ТаблицыТоваров
└── Таблица
    └── Строка
        └── Ячейка
```

Задача `DR_DocumentProcessor` состоит не только в переносе этих значений.

OCR может представить одну и ту же визуальную таблицу разным количеством физических колонок. Поэтому перед созданием `Document.ТабличнаяЧасть` необходимо построить логическую схему таблицы и привести физические данные OCR к этой схеме.

Общий процесс:

```text
ТаблицыТоваров
      ↓
определение заголовков
      ↓
СоздатьСхемуКолонок()
      ↓
логическая схема
      ↓
обработка каждой OCR-таблицы
      ↓
ОпределитьВариантСхемыТаблицы()
      ↓
РазобратьСтрокуПоСхеме()
      ↓
нормализованные строки
      ↓
СоздатьТаблицуТоваров()
      ↓
ТаблицаЗначений
      ↓
ЗаполнитьТабличнуюЧасть()
      ↓
Document.ТабличнаяЧасть
```

---

# 2. Причина существования логической схемы

Количество колонок, визуально существующих в документе, и количество ячеек, возвращенных OCR, могут различаться.

Например, исходная таблица содержит:

```text
| Товар | Количество | Цена |
| Товар A | 10 шт | 500 |
```

OCR может вернуть строку как:

```text
["Товар A", "10 шт", "500"]
```

В этом случае существует три физических ячейки.

Но другой OCR-результат той же строки может выглядеть как:

```text
["Товар A", "10", "шт", "500"]
```

Здесь физических ячеек уже четыре.

Для DoRIS оба варианта должны привести к одинаковой логической структуре:

```text
Номенклатура
Количество
Единица измерения
Цена
```

Поэтому в алгоритме используются два разных понятия:

**Физическая колонка** — ячейка, фактически возвращенная OCR.

**Логическая колонка** — колонка нормализованной таблицы DoRIS.

Количество физических и логических колонок не обязано совпадать.

---

# 3. Точка входа обработки таблиц

Основная функция области:

```bsl
РазобратьТаблицыТоваров(ДокументOCR)
```

Она вызывается из:

```bsl
РазобратьДокументOCR()
```

После обработки полученная `ТаблицаЗначений` передается в:

```bsl
ЗаполнитьТабличнуюЧасть()
```

Таким образом:

```text
ДокументOCR
      ↓
РазобратьТаблицыТоваров()
      ↓
ТаблицаЗначений
      ↓
ЗаполнитьТабличнуюЧасть()
      ↓
Document.ТабличнаяЧасть
```

---

# 4. Формат входных данных

`ДокументOCR.ТаблицыТоваров` является массивом таблиц.

Упрощенный пример:

```text
ТаблицыТоваров[0]
    [0] = ["№", "Товар", "Количество", "Цена"]
    [1] = ["1", "Товар A", "10 шт", "500"]
    [2] = ["2", "Товар B", "5 шт", "700"]

ТаблицыТоваров[1]
    [0] = ["3", "Товар C", "8 шт", "400"]
    [1] = ["4", "Товар D", "12 шт", "900"]
```

Первая таблица имеет специальное значение.

Ее первая строка считается строкой заголовков.

Последующие таблицы рассматриваются как продолжение первой таблицы и обрабатываются по уже построенной схеме.

---

# 5. Построение схемы колонок

Схема создается функцией:

```bsl
СоздатьСхемуКолонок(ДокументOCR)
```

В качестве источника схемы используется первая OCR-таблица:

```text
ДокументOCR.ТаблицыТоваров[0]
```

Первая строка этой таблицы принимается за заголовок:

```bsl
ПерваяТаблица = ДокументOCR.ТаблицыТоваров[0];
Заголовки = ПерваяТаблица[0];
```

На основании заголовков создается массив структур.

Каждая логическая колонка описывается структурой:

```text
Колонка
├── Имя
├── Расширяемая
└── ИмяДополнительнойКолонки
```

Например:

```text
Имя = "Товар"
Расширяемая = Ложь
ИмяДополнительнойКолонки = ""
```

или:

```text
Имя = "Количество"
Расширяемая = Истина
ИмяДополнительнойКолонки = "ДобЕдИзм"
```

---

# 6. Расширяемые колонки

Некоторые физические колонки OCR могут содержать несколько логических значений.

Правила таких колонок задаются функцией:

```bsl
ПолучитьПравилаРасширенияКолонок()
```

В версии 0.1 beta реализовано одно правило:

```text
Количество
    ↓
ДобЕдИзм
```

То есть значение:

```text
"10 шт"
```

может быть преобразовано в две логические колонки:

```text
Количество = "10"
ДобЕдИзм = "шт"
```

`ДобЕдИзм` является внутренним именем дополнительной колонки.

Оно используется специально для исключения конфликта с колонкой единицы измерения, которая уже могла присутствовать в исходной OCR-таблице.

Архитектура правил позволяет в дальнейшем добавлять другие расширяемые колонки, однако в версии 0.1 beta реализовано только правило для `Количество`.

---

# 7. Определение расширения схемы

При создании схемы сравнивается количество заголовков и количество физических ячеек первой строки данных:

```text
КоличествоКолонокЗаголовка
КоличествоКолонокСтроки
```

Вычисляется:

```text
РазницаКолонок =
    КоличествоКолонокСтроки -
    КоличествоКолонокЗаголовка
```

После этого для каждой расширяемой колонки определяется необходимость добавления дополнительной логической колонки.

Используются три условия.

## 7.1. Объединенное значение

Первый вариант возникает, когда число физических колонок совпадает с заголовком, но значение расширяемой колонки содержит числовую и строковую части.

Например:

```text
Заголовок:
Количество

Значение:
10 шт
```

Проверка выполняется функцией:

```bsl
ПроверитьПоследнийСимволВСтроке()
```

Если последний значимый символ значения не является цифрой, значение рассматривается как потенциально содержащее дополнительную строковую часть.

Для `Количество` это означает необходимость логической колонки `ДобЕдИзм`.

---

# 8. Дополнительная физическая колонка

Второй вариант:

```text
заголовок:
Товар | Количество | Цена

данные:
Товар A | 10 | шт | 500
```

Количество физических колонок больше количества заголовков.

Если в схеме существует только одна расширяемая колонка, дополнительная физическая колонка считается относящейся именно к ней.

В текущей версии такой колонкой является `Количество`.

Логическая схема становится:

```text
Товар
Количество
ДобЕдИзм
Цена
```

---

# 9. Несколько расширяемых колонок

Алгоритм также предусматривает общий случай:

```text
РазницаКолонок =
КоличествоРасширяемыхКолонок
```

Если количество дополнительных физических колонок равно количеству расширяемых колонок, предполагается, что каждая из расширяемых колонок получила дополнительную физическую колонку.

В версии 0.1 beta фактически используется только одно правило расширения, однако эта часть алгоритма не привязана непосредственно к `Количество`.

---

# 10. Логическая схема

Результатом `СоздатьСхемуКолонок()` является массив логических колонок.

Например исходный заголовок:

```text
№ | Товар | Количество | Цена
```

может создать схему:

```text
[0] №
[1] Товар
[2] Количество
[3] ДобЕдИзм
[4] Цена
```

Количество элементов этой схемы далее считается количеством **логических колонок**.

---

# 11. Обработка нескольких OCR-таблиц

После построения схемы выполняется обход:

```bsl
ДокументOCR.ТаблицыТоваров
```

Схема при этом повторно не строится.

Для таблицы с индексом `0`:

```text
ЕстьЗаголовок = Истина
```

и первая строка пропускается:

```text
НачальныйИндекс = 1
```

Для всех следующих таблиц:

```text
ЕстьЗаголовок = Ложь
НачальныйИндекс = 0
```

Таким образом DoRIS рассматривает последующие OCR-таблицы как продолжение товарной таблицы.

Например:

```text
Первая таблица:

№ | Товар | Количество | Цена
1 | A     | 10 шт      | 500
2 | B     | 20 шт      | 600
```

и следующая распознанная таблица:

```text
3 | C | 5 шт | 700
4 | D | 8 шт | 900
```

будут обработаны одной логической схемой.

---

# 12. Определение варианта физической схемы

Для каждой OCR-таблицы вызывается:

```bsl
ОпределитьВариантСхемыТаблицы()
```

Функция возвращает один из трех вариантов:

```text
ЛогическаяСхема
ОбъединеннаяСхема
НесовместимаяСхема
```

---

# 13. ЛогическаяСхема

`ЛогическаяСхема` означает, что физические значения могут последовательно переноситься в логические колонки.

Например:

```text
Логическая схема:

Товар | Количество | ДобЕдИзм | Цена
```

OCR:

```text
Товар A | 10 | шт | 500
```

Значения уже разделены физически и специальное разделение одной ячейки не требуется.

---

# 14. ОбъединеннаяСхема

`ОбъединеннаяСхема` означает, что расширяемая логическая колонка представлена одной физической ячейкой.

Например:

```text
Логическая схема:

Товар | Количество | ДобЕдИзм | Цена
```

OCR:

```text
Товар A | 10 шт | 500
```

Количество логических колонок:

```text
4
```

Количество физических:

```text
3
```

Одна физическая ячейка должна заполнить две логические колонки.

---

# 15. НесовместимаяСхема

Таблица получает `НесовместимаяСхема`, если ее невозможно безопасно сопоставить с построенной логической схемой.

В текущей реализации это происходит, в частности, если:

```text
КоличествоФизическихКолонок = 0
```

или:

```text
КоличествоФизическихКолонок >
КоличествоЛогическихКолонок
```

или отсутствует строка данных, по которой можно определить вариант схемы.

Несовместимая таблица не обрабатывается:

```bsl
Если ВариантСхемы = "НесовместимаяСхема" Тогда
    Продолжить;
КонецЕсли;
```

То есть ошибка отдельной таблицы не останавливает обработку всего OCR-документа.

---

# 16. Определение объединенной схемы

Для расширяемых колонок анализируется значение первой строки данных таблицы.

Используются функции:

```bsl
ПолучитьЧисловуюЧасть()
ПолучитьСтроковуюЧасть()
```

Если:

```text
СтроковаяЧасть <> ""
```

таблица определяется как:

```text
ОбъединеннаяСхема
```

В противном случае:

```text
ЛогическаяСхема
```

Таким образом тип схемы определяется для таблицы, после чего один и тот же вариант применяется ко всем ее строкам.

---

# 17. Разбор строки

Каждая строка данных передается в:

```bsl
РазобратьСтрокуПоСхеме(
    СтрокаТаблицы,
    СхемаКолонок,
    ВариантСхемы)
```

Ключевой особенностью функции являются два независимых индекса:

```text
ИндексЛогическойКолонки
ИндексФизическойКолонки
```

Это необходимо потому, что:

```text
КоличествоЛогическихКолонок
```

может отличаться от:

```text
КоличествоФизическихКолонок
```

---

# 18. Обычный перенос значения

В обычном случае:

```text
physical[0] → logical[0]
physical[1] → logical[1]
physical[2] → logical[2]
```

После переноса:

```text
ИндексФизическойКолонки += 1
ИндексЛогическойКолонки += 1
```

---

# 19. Разбор объединенной колонки

Особый случай возникает при выполнении двух условий:

```text
ВариантСхемы = "ОбъединеннаяСхема"
```

и:

```text
Колонка.Расширяемая = Истина
```

Значение физической ячейки разделяется:

```bsl
ЧисловаяЧасть = ПолучитьЧисловуюЧасть(Значение);
СтроковаяЧасть = ПолучитьСтроковуюЧасть(Значение);
```

Например:

```text
"10 шт"
```

дает:

```text
ЧисловаяЧасть  = "10"
СтроковаяЧасть = "шт"
```

В результат добавляются сразу два значения:

```text
logical[n]     = "10"
logical[n + 1] = "шт"
```

При этом была использована только одна физическая ячейка.

Поэтому индексы изменяются неодинаково:

```text
ИндексФизическойКолонки += 1
ИндексЛогическойКолонки += 2
```

Именно независимое управление двумя индексами обеспечивает нормализацию объединенных OCR-ячеек.

---

# 20. Получение числовой части

Функция:

```bsl
ПолучитьЧисловуюЧасть()
```

последовательно читает начало строки.

Допускаются:

```text
0–9
-
,
.
пробел
неразрывный пробел
```

Пробелы в результирующее значение не добавляются.

Чтение прекращается при первом символе, который не относится к допустимой числовой части.

Например:

```text
"1 000,50 шт"
```

преобразуется в числовую часть:

```text
"1000,50"
```

---

# 21. Получение строковой части

Функция:

```bsl
ПолучитьСтроковуюЧасть()
```

удаляет из исходного значения цифры и сокращает пробелы.

Для текущего алгоритма она используется прежде всего для определения и извлечения единицы измерения из объединенного значения количества.

---

# 22. Недостающие физические ячейки

OCR может вернуть строку короче логической схемы.

Например логическая схема содержит:

```text
Товар | Количество | ДобЕдИзм | Цена | Сумма
```

а OCR-строка закончилась после `Цена`.

Если:

```text
ИндексФизическойКолонки >=
СтрокаТаблицы.Количество()
```

в соответствующую логическую колонку добавляется:

```text
""
```

и обработка логических колонок продолжается.

В результате все нормализованные строки имеют структуру, соответствующую логической схеме.

---

# 23. Пример полной нормализации

Исходный OCR:

```text
Таблица 1

["№", "Товар", "Количество", "Цена"]
["1", "Товар A", "10 шт", "500"]
["2", "Товар B", "5 шт", "700"]
```

На основании заголовка и первой строки создается схема:

```text
№
Товар
Количество
ДобЕдИзм
Цена
```

Для таблицы определяется:

```text
ОбъединеннаяСхема
```

Строка:

```text
["1", "Товар A", "10 шт", "500"]
```

преобразуется в:

```text
["1", "Товар A", "10", "шт", "500"]
```

Следующая:

```text
["2", "Товар B", "5 шт", "700"]
```

в:

```text
["2", "Товар B", "5", "шт", "700"]
```

В результате физическое представление OCR больше не имеет значения для последующих этапов.

---

# 24. Пример физически разделенных значений

OCR может вернуть:

```text
["№", "Товар", "Количество", "Цена"]
["1", "Товар A", "10", "шт", "500"]
```

Схема также будет расширена:

```text
№
Товар
Количество
ДобЕдИзм
Цена
```

Но данные уже содержат необходимое количество физических колонок.

Для таблицы используется:

```text
ЛогическаяСхема
```

и результат будет таким же:

```text
["1", "Товар A", "10", "шт", "500"]
```

Таким образом оба OCR-представления:

```text
"10 шт"
```

и:

```text
"10" | "шт"
```

приводятся к одной структуре.

---

# 25. Создание ТаблицыЗначений

После нормализации всех строк вызывается:

```bsl
СоздатьТаблицуТоваров()
```

На этом этапе массивы превращаются в стандартную `ТаблицаЗначений` платформы 1С.

Для сопоставления OCR-заголовков с полями DoRIS используется:

```bsl
DR_DocumentFactory.СоответствиеКолонок()
```

Например OCR-заголовок:

```text
Товар
```

может быть сопоставлен с:

```text
Номенклатура
```

---

# 26. Неизвестные колонки

Если для OCR-заголовка отсутствует соответствие, колонка не отбрасывается.

Для нее создается техническое имя:

```text
Колонка1
Колонка2
...
```

При этом исходное имя OCR используется как заголовок колонки `ТаблицаЗначений`.

Это позволяет сохранить распознанные данные даже в случае появления неизвестной DoRIS колонки.

---

# 27. Перенос в Document

Полученная `ТаблицаЗначений` передается в:

```bsl
ЗаполнитьТабличнуюЧасть()
```

Для каждой строки создается:

```bsl
Документ.ТабличнаяЧасть.Добавить()
```

После чего выполняется:

```bsl
ЗаполнитьЗначенияСвойств()
```

Таким образом значения одноименных полей переносятся из нормализованной `ТаблицаЗначений` в строку универсального `Document`.

---

# 28. Преобразование числовых значений

После заполнения строки некоторые поля преобразуются из строкового представления OCR в число.

В версии 0.1 beta это:

```text
Количество
Цена
Сумма
СуммаНДС
СуммаБезНДС
```

Для преобразования используется:

```bsl
СтроковыеФункцииКлиентСервер.СтрокаВЧисло()
```

Для незаполненных значений `Цена`, `Сумма`, `СуммаНДС` и `СуммаБезНДС` устанавливается `0`.

`Количество` преобразуется непосредственно без предварительной проверки `ЗначениеЗаполнено()`.

# 30. Ответственность OCR-провайдера и DocumentProcessor

Очень важно не переносить описанную логику в OCR-провайдер.

Провайдер отвечает за преобразование собственного API-ответа в промежуточную модель OCR:

```text
PaddleOCR / Mistral / другой OCR
                ↓
          собственный JSON
                ↓
           OCR Provider
                ↓
       МассивДокументов
                ↓
       ├── СтрокиДокумента
       └── ТаблицыТоваров
```

`DR_DocumentProcessor` начинает работу только после получения этой унифицированной структуры.

Поэтому новый OCR-провайдер обязан привести собственное представление таблиц к контракту `ТаблицыТоваров`.

Алгоритм нормализации логических и физических колонок остается общей частью DoRIS и не должен дублироваться в провайдерах.

---

# 31. Ограничения версии 0.1 beta

Текущий алгоритм имеет ряд намеренных ограничений, соответствующих состоянию проекта.

Схема строится только по первой OCR-таблице.

Первая строка первой таблицы считается заголовком.

При построении схемы физическая структура определяется по первой строке данных первой таблицы.

Вариант схемы каждой следующей таблицы также определяется по ее первой строке данных.

В версии 0.1 beta существует только одно правило расширения:

```text
Количество → ДобЕдИзм
```

Таблица с количеством физических колонок больше количества логических считается несовместимой и пропускается.

`СтрокиДокумента` не участвуют в алгоритме обработки товарных таблиц.

Распознавание реквизитов документа находится вне текущего рабочего pipeline и будет развиваться в следующих версиях.

---

# 32. Требования при изменении алгоритма

При развитии области `Таблицы` необходимо сохранять основное разделение уровней:

```text
OCR Provider
    ↓
промежуточная модель OCR
    ↓
DR_DocumentProcessor
    ↓
логическая нормализация
    ↓
Document
```

Provider-specific особенности API не должны попадать в алгоритм таблиц.

`DR_DocumentProcessor` не должен анализировать исходный JSON PaddleOCR, Mistral OCR или другого провайдера.

Добавление нового OCR-провайдера не должно требовать изменения алгоритма таблиц, если новый провайдер соблюдает контракт промежуточной модели OCR.

Изменения правил нормализации таблиц должны выполняться централизованно в `DR_DocumentProcessor`.

# 33. Функции области Таблицы

В версии 0.1 beta область содержит следующие функции и процедуры.

### `РазобратьТаблицыТоваров()`

Главный координатор обработки товарных таблиц.

Строит схему, определяет вариант каждой таблицы, нормализует строки и создает итоговую `ТаблицаЗначений`.

### `СоздатьТаблицуТоваров()`

Преобразует нормализованные массивы строк в `ТаблицаЗначений` и применяет соответствия имен колонок DoRIS.

### `РазобратьСтрокуПоСхеме()`

Сопоставляет физические ячейки OCR с логическими колонками схемы.

Выполняет разделение объединенных значений.

### `СоздатьСхемуКолонок()`

Создает логическую схему на основании заголовка и первой строки первой OCR-таблицы.

### `ПолучитьПравилаРасширенияКолонок()`

Возвращает список правил расширения логических колонок.

### `ПолучитьПравилоРасширенияКолонки()`

Ищет правило расширения для конкретного имени OCR-колонки.

Сравнение выполняется без учета регистра и внешних пробелов.

### `ДобавитьДополнительнуюКолонку()`

Создает и вставляет дополнительную логическую колонку после расширяемой.

В текущем рабочем алгоритме непосредственно не вызывается.

### `ПолучитьКоличествоФизическихКолонок()`

Определяет количество физических колонок по первой строке данных OCR-таблицы.

Учитывает наличие строки заголовков.

### `ОпределитьВариантСхемыТаблицы()`

Классифицирует OCR-таблицу как:

```text
ЛогическаяСхема
ОбъединеннаяСхема
НесовместимаяСхема
```

# 34. Связанные служебные функции

Область `Таблицы` использует служебные функции:

```bsl
ПолучитьСтроковуюЧасть()
ПолучитьЧисловуюЧасть()
ПроверитьПоследнийСимволВСтроке()
```

Они расположены в области `Служебные` модуля `DR_DocumentProcessor`, но являются частью фактического алгоритма нормализации таблиц.

При изменении их поведения необходимо учитывать влияние на:

```text
построение схемы
определение ОбъединеннойСхемы
разделение значений
```

# 35. Основной инвариант алгоритма

Главное требование к области `Таблицы` можно сформулировать следующим образом:

> Различное физическое представление одной и той же товарной таблицы OCR-провайдером должно, насколько это позволяет известная логическая схема, приводиться к одинаковой структуре `Document.ТабличнаяЧасть`.

Именно для выполнения этого требования существуют:

```text
СхемаКолонок
Расширяемая колонка
ЛогическаяСхема
ОбъединеннаяСхема
ИндексЛогическойКолонки
ИндексФизическойКолонки
```

Эти понятия являются основой алгоритма обработки таблиц DoRIS 0.1 beta.
