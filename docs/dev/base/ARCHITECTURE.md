# Архитектура расширения

[README](README.md) · [Архитектура](ARCHITECTURE.md) · [Модули](MODULES.md) · [Цепочки](PIPELINES.md) · [Данные](DATA_AND_PROTOCOLS.md)

Снимок исходников 04.11.2026; серверный сервис 0.2 beta, Mobile 0.0.2 beta, протокол 2. Описание по коду, без запуска 1С, Flutter-приложения и OCR.

## Общий состав

Расширение содержит ядро OCR (RecognitionService, Settings, Validation, HttpClient, три провайдера, DocumentProcessor, DocumentFactory), обычную OCR-обработку, добавление команды в стандартное поступление, входящий мобильный HTTP-сервис, шесть общих модулей мобильного обмена и две формы его администрирования/обработки. Все общие модули серверные, непубличные глобально и непривилегированные; клиентские части форм отвечают за выбор файлов, вопросы и показ результата. Точный состав — MODULES.

## OCR

Константа DR_АктивныйАдаптер выбирает ключ записи DR_НастройкиАдаптера. DR_Settings связывает его с общим модулем провайдера. Сервис вызывает единый экспорт ВыполнитьРаспознавание(Настройки, СтруктураФайла), затем процессор. Процессор не выполняет сеть: читает массивы строк/таблиц, нормализует в Document. Фабрика печатает таблицу либо применяет Document к ссылке уже записанного поступления.

Изолированная переносимость на произвольную конфигурацию не следует из универсальной структуры Document.

## Транзакционные границы

HTTP/папка регистрируют приём без OCR. Мобильная форма отдельно устанавливает состояние/блокировки, получает и распознаёт оригинал без открытой транзакции заполнения. Только после валидации Document открывает транзакцию, перечитывает владельца/связь/права/версию, вызывает фабрику, проверяет строковую Ошибка и факт записи, фиксирует или откатывает. Состояние Распознан обновляется после фиксации отдельно. Блокировки редактирования удерживаются также во время OCR; они не являются открытой SQL-транзакцией.


[Навигация](../../../../base/docs/mobile/developer/README.md) · [Контракты модулей](../../../../base/docs/mobile/developer/MODULES.md)

```text

  │    DR_MobileHTTPService → DR_MobileHttp
  │      ├─ DR_MobileSettings: сетевой токен, пользователь ИБ, доступ/сеанс
  │      └─ DR_MobileMultipart: ограниченный бинарный разбор, metadata
  │
  └─ Incoming/<UUID>/document.json + оригиналы
       явный административный «Импорт» → DR_MobileFolderImport
         ├─ DR_MobileSettings: файловый токен → фактический владелец
         └─ DR_MobileMultipart: строгий JSON и общий валидатор metadata
                      │
                      ▼
       DR_MobileStorage.ПроверитьПовтор / Зарегистрировать
         ├─ ключ: UUID пользователя ИБ + UUID документа
         ├─ DR_MobileFiles: .pending-* → Documents/<владелец>/<UUID>
         └─ регистр DR_ПринятыеМобильныеДокументы → COMMIT → квитанция
                      │
       ┌──────────────┴──────────────────────┐
       ▼                                     ▼
  HTTP-ответ / GET                   после файлового приёма:
                                    проверка и очистка одного пакета Incoming

Форма DR_ОбработкаМобильныхДокументов
  ├─ чтение/отбор/сортировка, контрагент, ссылка на поступление
  └─ явное «Распознать» для одной отмеченной строки
       DR_MobileStorage → первый зарегистрированный оригинал
         → временное хранилище → DR_RecognitionService
         → существующий провайдер / DR_DocumentProcessor
         → DR_DocumentFactory.ПечатьНакладная / МакетТаблица
```

## Ответственность

| Компонент | Граница |
|---|---|
| HTTPService.DR_MobileHTTPService | Четыре маршрута; тонкие обработчики передают запрос DR_MobileHttp |
| DR_MobileHttp | Авторизация HTTP, согласованность заголовков, безопасные JSON-ответы, журнал request_id/code; сам OCR не запускает |
| DR_MobileSettings | Канонические настройки пользователя, разрешение, сопоставление учётной записи, независимые токены, адрес/корень, QR |
| DR_MobileMultipart | HTTP framing/лимиты, строгий JSON, имена/порядок/MIME; не декодирует изображения/PDF |
| DR_MobileFolderImport | Один нерекурсивный проход Incoming, файловая авторизация, состав пакета, вызов общего регистратора, отдельная очистка |
| DR_MobileFiles | Проверка серверных путей, служебные каталоги, staging/публикация, маркер принадлежности, уборка только собственной временной операции |
| DR_MobileStorage | Квитанции и duplicate, транзакционная регистрация, чтение зарегистрированного оригинала, контрагент/связь/состояния и доступ формы |
| Форма настроек | Административные команды, маскировка токенов, временный QR; не определяет владельца пакета |
| Форма обработки | Представление списка, явный импорт, ручная связь с поступлением, синхронный серверный OCR и показ результата |
| DR_RecognitionService | Существующий OCR-конвейер. Здесь документируется только вход/выход мобильного вызова |

## Хранение и атомарность

Регистр хранит историю, манифест и путь. Новые оригиналы — файлы в `Documents/<UUID пользователя ИБ>/<UUID документа>`. Исторический ресурс `Оригиналы` сохранён, но новая регистрация его не заполняет; текущий читатель использует файловый каталог, не мигрирует старые бинарные данные.

Файловая система не входит в транзакцию СУБД. DR_MobileFiles готовит соседний `.pending-<UUID операции>` с `doris-operation.json`. Регистратор под исключительной блокировкой полного ключа повторяет доступ/duplicate, публикует файлы, записывает строку и фиксирует транзакцию. При ошибке очищается только известный временный каталог; конечные файлы не удаляются из-за возможного неопределённого COMMIT. Маркер позволяет проверить собственный конечный набор при следующей **явной** попытке. Автоматического сканирования и восстановления всего хранилища нет.

Равенство определяется типом документа, заявленным количеством страниц, упорядоченными именами, номерами и фактическими размерами файлов. Хеширования или сравнения всех байтов нет. Повтор не создаёт новую строку, дату, источник или transaction_id и не требует чтения зарегистрированных оригиналов. [Детали pipeline](../../../../base/docs/mobile/developer/PIPELINE.md).

## Права и доверенные границы

HTTP выполняется в техническом контексте публикации; обычные серверные модули имеют Privileged=false и ServerCall=false. Прикладной пользователь извлекается только из сетевого токена и проверяется через БСП. Для HTTP требуется отдельный интерактивный сеанс этого пользователя; служебный сеанс текущего запроса не подходит.

Файловый импорт требует роли DR_АдминистрированиеМобильногоОбмена у вызывающего. Выбранный в форме пользователь задаёт источник Incoming, но владелец каждого пакета и его корень оригиналов берутся из файлового токена. Интерактивный сеанс владельца для файлового приёма не требуется.

Форма обработки требует Use на обработку и однозначного соответствия текущего пользователя каталога текущей учётной записи ИБ. Обычный пользователь видит свои документы, администратор обмена может выбирать владельца или всех. Серверные методы повторно проверяют ключ: изменяемые клиентские отборы и ссылки не являются основанием доступа. Сами роли регистра не содержат построчного RLS-ограничения; нельзя переносить гарантии этой формы на произвольный внешний код/иные роли. [Точные права](../../../../base/docs/mobile/developer/DATA_MODEL.md).

Сервис не настраивает IIS/Apache, учётную запись публикации, сетевые ACL и облачную доставку. Пути проверяются лексически; разрешение reparse points/символьных ссылок и полная защита от внешней подмены между проверкой и I/O не реализованы. Каталоги должны контролироваться администратором и службой 1С.

Серверного календарного запрета передачи в этих модулях нет. Ограничение Mobile после 30.12.2026 относится к мобильному клиенту; серверный приём и ручной импорт отдельной проверкой этой даты не ограничиваются.


## Ограничения ядра

Обычный старый вызов с целью не передаёт ОчищатьТовары, а локальный флаг сервиса в такой ветке явно не инициализируется. Новый мобильный путь обходит эту неопределённость: OCR без цели и фабрика с явным третьим Истина. Сервис даже в подготовительном вызове создаёт ТабДокумент, что даёт лишнюю работу/точку ошибки. Реквизиты шапки Document не означают их фактическую запись фабрикой. Обработка объединённых ячеек/всех вариантов печатных форм ограничена. ТипАдаптера присутствует в хранении, но не завершён как единый механизм выбора/валидации в UI.
