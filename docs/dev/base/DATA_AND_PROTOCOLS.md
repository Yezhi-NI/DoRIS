## Настройки и универсальные структуры OCR

DR_АктивныйАдаптер — строка ключа провайдера; DR_ПоказатьТабличныйДокумент — общая булева константа; DR_АдресПубликацииМобильногоОбмена — Строка(255). DR_НастройкиАдаптера хранит Провайдер и ресурсы АдресСервиса, АдресРесурса, Порт, Таймаут, ApiKey, Промпт, ТипАдаптера. Ключ API — серверный секрет, не мобильный токен. Режим выбора значения ТипАдаптера в форме закомментирован; текущий тип по умолчанию определяется ключом провайдера.

Настройки runtime: ПровайдерOCR (общий модуль), Сервер, АдресСервиса (путь ресурса), ApiKey, Промпт, ТаймаутHTTP, ИнтервалОпроса=2, МаксимальноеКоличествоОпросов=300, Порт, ТипАдаптера, ТипОтветаПоУмолчанию. Local по умолчанию 127.0.0.1:8765, /ocr, 180 секунд; это отдельный HTTP-адаптер, не опрос облачной задачи.

Вход сервиса — Массив структур ФайлРаспознавания(АдресФайла,ТипФайла), ОбъектЗаполнения и необязательное свойство ОчищатьТовары. Возврат — адрес массива результатов во временном хранилище. Параметр ВозвращатьDocument=Ложь сохраняет старый возврат без Document; Истина сохраняет поле. Сервис при пустой цели не вызывает заполнение, но формирует ТабДокумент при успехе.

Процессор возвращает внешнюю структуру Document/Markdown/JSON/Ошибка. Document содержит ТипОбъекта, ТипДокумента, МассивСтрок, РеквизитыДокумента и ТабличнаяЧасть. Markdown в этой оболочке первоначально пустой, JSON — исходный JSONОтвет провайдера. При ошибке Document=Неопределено. Пустая Ошибка сама по себе не гарантирует товары. ТабличнаяЧасть: НомерСтроки, Номенклатура, ЕИ, ДобЕдИзм, Количество, Цена, СуммаБезНДС, СуммаНДС, Сумма, GTIN, NTIN, СтавкаНДС, Артикул, Код. Это ТаблицаЗначений, не клиентский JSON.

Фабрика СоздатьДокумент(Документ, ОбъектЗаполнения, ОчищатьТовары=Ложь) принимает именно внешнюю оболочку с .Document и ссылку на поступление. Возвращает оболочку с .Ошибка: успех — строка пустая; ошибка — строка описания. Для нового мобильного заполнения Истина передаётся третьим позиционным параметром. Ошибка Неопределено/нестроковая не считается успехом. Самостоятельной фиксации транзакции фабрика не выполняет; обработчик формы откатывает также возвращённую ошибку.

| [DR_АдминистрированиеМобильногоОбмена](../../../../base/Roles/DR_АдминистрированиеМобильногоОбмена/Ext/Rights.xml) | Read/View Пользователей; View общей формы/команды; Read/Update/View принятых; Read/Update/View/Edit настроек и адресной константы |

Административная роль сама не добавляет Use обработки: для её работы нужны соответствующие права, например через DR_МобильныйОбмен. Имя «администратор» в интерфейсе не заменяет проверяемую роль. В Configuration.xml DefaultRoles содержит DR_ОсновнаяРоль; автоматическое назначение мобильных ролей всем пользователям не следует из их регистрации в ChildObjects. У DR_ОсновнаяРоль отдельного Rights.xml в снимке нет; фактический профиль пользователя ИБ здесь не определяется.

Модули не привилегированы. Серверная форма ограничивает обычного пользователя его UUID, администратор обмена может видеть всех; это **проверки конкретной формы/API**, а не RLS всей таблицы: ограничения записей в этих Rights.xml отсутствуют. Права на целевое поступление, его выбор/создание/запись/открытие обеспечиваются основной конфигурацией и другими ролями; мобильная роль их явно не выдаёт.

Для OCR дополнительно требуется чтение DR_АктивныйАдаптер и DR_НастройкиАдаптера с используемыми ресурсами, доступ к провайдеру/макету. Одной DR_МобильныйОбмен недостаточно: она не даёт этих чтений. Регистр настроек адаптера содержит ApiKey; выдача чтения имеет последствия для доступа к секрету. Нужные действующие роли проверяются администратором, привилегированного обхода нет. ## Маршруты

Базовая публикация условно `https://example.invalid/accounting`. Таблица содержит добавляемую часть URL; RootURL сервиса — `doris`, ReuseSessions=DontUse. Сегмент `/v1/` исторический и не равен версии формата: `/info` сообщает протокол **2..2** и продукт **0.2 beta**.

| Метод / endpoint | Шаблон / обработчик HTTP-сервиса | Авторизация |
|---|---|---|
| POST `/hs/doris/v1/mobile/documents` | Документы / ДокументыPOST → ОбработатьPOST | Сетевой токен, разрешение, интерактивный сеанс владельца |
| GET `/hs/doris/v1/mobile/documents/{uuid}` | Документ / ДокументGET → ОбработатьGET | То же; выборка только владельца |
| GET `/hs/doris/v1/mobile/info` | Информация / ИнформацияGET → ОбработатьИнформациюGET | Без пользовательского токена |
| GET `/hs/doris/v1/mobile/auth/check` | ПроверкаПользователя / ПроверкаПользователяGET → ОбработатьПроверкуПользователяGET | Как для документов, но без чтения регистра принятых |

Для документов Accept после НРег/СокрЛП должен быть ровно `application/json`, query запрещён. GET не принимает Transfer-Encoding; Content-Length отсутствует либо `0`. Диагностические GET проверяют метод/query/framing, но не требуют Accept в своей функции проверки. Неверный метод может быть отклонён платформой ещё до BSL; приведённые JSON-ошибки относятся к запросам, достигшим обработчика.

Успешный `/info`: ровно application=`DoRIS`, server_version=`0.2 beta`, protocol_version=2, min_supported_protocol=2. Успешный `/auth/check`: authorized=true и username=имя пользователя ИБ. Эти ответы не создают документ, не возвращают оригиналы и не подтверждают OCR.

## Доступ

Прикладной секрет передаётся **только X-DoRIS-Token**. Токеном не являются имя пользователя, пароль публикации или UUID документа. Basic/Bearer для прикладной авторизации не реализованы. Техническое соединение публикации настраивает администратор окружения; модули не включают привилегированный режим.

`АвторизоватьЗапрос()` проверяет формат токена, `НайтиПользователяПоТокену()` требует одну каноническую запись, `ПолучитьПользователяИБ()` проверяет однозначное соответствие каталога Пользователи учётной записи ИБ. `ПроверитьДоступ()` подтверждает разрешение и другой интерактивный сеанс того же UUID. Допустимые приложения сеанса: 1CV8, 1CV8C, WebClient, MobileClient. Текущий сеанс HTTP исключён; ошибка API сеансов — отказ 503, не разрешение.

Формат секрета: lowercase UUID v4 с допустимым variant либо ненулевые 64 lowercase HEX. Генератор сервера использует Новый УникальныйИдентификатор и ограниченную проверку коллизий; он не заявлен как криптографический генератор. UUID документов/владельца проверяется общим КорректныйUUID: 36 символов lowercase HEX/дефисы, ненулевой; версия UUID для документа этим валидатором не фиксируется.

## POST: заголовки и multipart

| Элемент | Правило |

| Content-Type | multipart/form-data с единственным параметром boundary |
| Idempotency-Key | Корректный UUID, равный metadata.document_id |
| Content-Encoding | Любое непустое значение → 415 |
| Transfer-Encoding | Непустое значение → 400; chunked не входит в профиль |

Тело читается порциями по 64 KiB в ограниченный поток памяти: максимум **51 MiB (53 477 376)**. Это не потоковая запись оригиналов прямо на диск и не обещание отсутствия предшествующей буферизации веб-сервером.

Boundary длиной 1..70 ASCII-символов из разрешённого набора, не заканчивается пробелом; цитирование поддерживается. Framing CRLF, обязательный CRLF после закрывающей границы, без преамбулы/эпилога. Поиск delimiter бинарный (Horspool с KMP fallback), полное тело не переводится в строку.

Первая часть — **metadata**, без filename, Content-Type application/json; charset при наличии UTF-8. Затем **1..100** частей с одинаковым name=`files`, filename точно по metadata и Content-Type, согласованным с типом/расширением. Заголовки части — только content-disposition и content-type, по одному каждого, не более 8 KiB на блок. Дополнительные части или иной порядок отвергаются.

Metadata — строгий UTF-8 JSON без BOM, комментариев, дублированных ключей и лишнего корня, до **32 KiB**, до 2000 JSON-токенов и глубины 8. Точная схема image (UUID искусственный):

```json
{
  "document_id": "11111111-1111-4111-8111-111111111111",
  "document_type": "image",
  "page_count": 2,
  "files": [
    {"filename": "page_001.jpg", "page_number": 1},
    {"filename": "page_002.png", "page_number": 2}
  ]
}
```

PDF: document_type=`pdf`, files содержит один `{filename:"document.pdf", page_number:null}`, page_count — целое 1..1000. Image: page_count=число файлов, целое 1..100, page_number=1..N по порядку. Поля size в request metadata нет; сервер измеряет части. Лишние поля в metadata и её элементах запрещены.

Имена уникальные, 1..128 символов ASCII букв/цифр/`_-.`, не начинаются точкой, не содержат путей. JPEG: расширение jpg/jpeg и MIME image/jpeg; PNG: png и image/png; PDF: document.pdf и application/pdf. Каждый оригинал непустой и не больше **20 MiB**, сумма не больше **50 MiB**. Эти серверные ограничения шире лимитов создания новых документов Mobile; сервер их автоматически до двух изображений не сокращает.

**Внутреннее содержимое файлов не декодируется.** Соответствие MIME/расширения и размеров не доказывает, что JPEG/PNG/PDF читается OCR. PDF page_count здесь заявлен клиентом, не вычислен на сервере.

## Квитанции и идемпотентность

Новая регистрация после COMMIT — **201 accepted**, равный повтор — **200 duplicate**. Пример одностраничной квитанции с условными UUID/размером:

```json
{
  "accepted": true,
  "document_id": "11111111-1111-4111-8111-111111111111",
  "status": "accepted",
  "transaction_id": "22222222-2222-4222-8222-222222222222",
  "received_at": "2026-11-01T07:00:00Z",
  "manifest": {
    "document_type": "image",
    "page_count": 1,
    "files": [{"filename": "page_001.jpg", "page_number": 1, "size": 12345}]
  }
}
```

Для duplicate меняется status, исходные transaction_id/received_at сохраняются. received_at формируется из **ДатаПриемаUTC**, без повторного пересчёта локальной даты. Все успешные/ошибочные ответы BSL: application/json; charset=utf-8, без BOM, Cache-Control=no-store, X-Request-Id, не более 64 KiB. POST 201 добавляет относительный Location `documents/<UUID>`, Host клиента не используется как доверенный origin.

Уникальность — `(UUID владельца ИБ, UUID документа)`. `МанифестыРавны()` сравнивает document_type/page_count, число и порядок files, filename/page_number/size. Разные владельцы могут иметь один document_id. Содержимое равной длины не сравнивается побайтово. Duplicate не читает сохранённые оригиналы и не меняет даты, источник, состояние OCR, связи и квитанцию; отсутствие оригинала не делает документ новым.

GET найденной строки возвращает **200 accepted** с тем же manifest/квитанцией даже после обработки OCR; это не status состояния OCR. GET отсутствующего UUID владельца возвращает 404. На сервере нет автоматически запускаемого POST после GET. Клиент сам сохраняет неопределённость и решает о явной проверке; GET не доказывает равенство оригинальных байтов.

## Ошибки и диагностика

```json
{
  "accepted": false,
  "document_id": "11111111-1111-4111-8111-111111111111",
  "status": "conflict",
  "error": {"code": "uuid_content_conflict", "message": "UUID уже использован для другого содержимого."},
  "request_id": "33333333-3333-4333-8333-333333333333"
}
```

До проверки UUID document_id=null. status: 404→not_found, 409→conflict, 5xx→error, остальные→rejected.

| Код | error.code | Причина |
|---|---|---|
| 400 | invalid_request | UUID, framing, metadata, JSON, порядок, недопустимый запрос |
| 401 | authentication_required / invalid_token | Отсутствующий/неверный токен или учётная запись |
| 403 | mobile_access_denied / user_session_required | Запрет обмена либо нет интерактивного сеанса |
| 404 | document_not_found | GET: у владельца нет зарегистрированного UUID |
| 409 | uuid_content_conflict | Тот же ключ, другой минимальный манифест |
| 411 | content_length_required | Нет Content-Length POST |
| 413 | size_limit_exceeded | Превышение размера/количества |
| 415 | unsupported_media_type | Неподдерживаемые Content-Type/Content-Encoding/MIME/расширение |
| 503 | temporarily_unavailable / session_check_unavailable | Блокировка регистрации либо недоступна проверка сеансов |
| 500 | internal_error | Непредвиденный сбой, включая файловое хранение или пустой UTC старой записи |

Сообщения для invalid_file/422 и rate_limited/429 остались в вспомогательном коде, но действующие пути мобильного приёма не реализуют декодирование файлов или rate limiter. Не следует описывать их как выполняемые проверки. Для 503/429 фабрика ошибок задаёт Retry-After=3; это не очередь/автоматический повтор.

Журнал DoRIS.MobileHTTP записывает request_id и код, без токена и исходного исключения; сбой журнала не меняет результат. Дополнительные замеры DoRIS.MobileHTTP.Timing по этапам существуют, но ДиагностикаВремениВключена() возвращает Ложь. Включение не выполнялось. Проверка повторяющихся заголовков возможна только в представлении, переданном платформой; framing/двойные заголовки, нормализуемые веб-сервером до BSL, требуют корректной настройки edge. Ответы платформы/прокси вне BSL могут отличаться от этой схемы.

## Каталоги

ПутьКПапке — сохранённый корень конкретного пользователя. Служба 1С должна видеть его и иметь права чтения/создания/записи; путь на телефоне или клиентском компьютере сам по себе не является серверным путём.

```text
<корень источника>/
  Incoming/
    <UUID документа>/
      document.json
      page_001.jpg                # либо JPEG/PNG в порядке files

<корень владельца токена>/
  Documents/
    <UUID пользователя ИБ>/
      <UUID документа>/
        page_001.jpg              # для PDF: document.pdf
        doris-operation.json      # принадлежность серверной операции
      .pending-<UUID операции>/   # только стадия подготовки
```

Корни могут совпадать, но имя Documents-владельца всегда UUID **пользователя ИБ**, не секретный токен, не UUID каталога Пользователи и не UUID текущего импортёра. Входной формат не содержит каталога токена/владельца на мобильном устройстве. Один Incoming может содержать пакеты разных разрешённых пользователей; выбранный пользователь формы определяет только источник.

Настройка «Сохранить» вызывает ПодготовитьКаталогиОбмена: существующий абсолютный корень, до 250 символов, затем создание отсутствующих Documents/Incoming. Поддержаны Windows drive-path и UNC; BSL также допускает абсолютный Unix-путь. Для Windows ПутьВнутри формирует `\`, для Unix `/`; имя потомка проверяется отдельно от абсолютного корня, точки/разделители не дают выхода к родителю. Полный каталог документа ограничен 255 символами, поэтому корень длиной 250 ещё не гарантирует пригодность для конкретного UUID.

Новые служебные имена канонические Documents/Incoming. Единственный существующий вариант другого регистра используется без переименования. Несколько вариантов, отличающихся только регистром, либо обычный файл с таким именем — конфликт, новый параллельный каталог не создаётся. Проверки пересечения Incoming с Documents и ранее зарегистрированными каталогами обязательны. Символьные ссылки/reparse points и внешняя подмена между проверкой/I/O не разрешаются в физические пути этим кодом: нужны доверенные каталоги и ACL окружения.

## document.json, версия 2

JSON строго UTF-8, без BOM/дублей ключей/комментариев, размер **1..32768 байт**. Ровно поля format/version/document_id/token/document_type/page_count/files; ровно filename/page_number/size для файла.

```json
{
  "format": "DoRIS.FileExchange",
  "version": 2,
  "document_id": "11111111-1111-4111-8111-111111111111",
  "token": "<ФАЙЛОВЫЙ_ТОКЕН>",
  "document_type": "image",
  "page_count": 1,
  "files": [{"filename": "page_001.jpg", "page_number": 1, "size": 12345}]
}
```

Это схема с невалидным заполнителем секрета, не пакет для запуска импорта. UUID искусственный, size условный. version должно численно равняться 2, document_id — точно имени UUID-каталога. Для PDF — один document.pdf, page_number=null, page_count 1..1000; изображений до 100, номера 1..N, JPEG/PNG. Общие правила имён/metadata повторно использует DR_MobileMultipart. Размер файла целый 1..20 MiB, сумма до 50 MiB; фактические длины должны совпасть. Любые лишние файлы и вложенные каталоги запрещены. Расширение проверяется, декодирования и проверки сигнатуры содержимого нет.

АвторизоватьФайловыйТокен требует каноническую запись, единственное соответствие в обеих колонках токенов, отдельный файловый секрет, разрешение и однозначного пользователя ИБ. Сетевой токен как файловый отвергается. Под блокировкой нового документа регистрация повторяет проверку отзыва/перевыпуска. Пакет содержит секрет в открытом JSON: читатели/права папки имеют значение. QR v3 выдаёт оба токена; это не тот же JSON, что document.json.

## Явный импорт и duplicate

Команда «Импорт» рабочей формы вызывает Импортировать. Один проход `НайтиФайлы(Корень, "*", Ложь)`: только прямые подкаталоги, без рекурсии; посторонние обычные файлы в корне пропускаются. Лимита МаксимумДокументовЗаЗапуск текущая функция не применяет; наличие старого поля не означает реализацию квоты/фонового задания.

ПрочитатьОписаниеПакета и ПрочитатьФайлыПакета готовят document_id/manifest/ИсточникиФайлов, затем используется общий регистратор. Duplicate совпадает по owner+UUID+минимальному manifest, без сравнения байтов; первоначальные даты/квитанция/источник/состояние/ссылки сохраняются. Ошибка токена блокирует и повтор: уже известный UUID не освобождает от авторизации входного пакета.

Повтор не зависит от нового пути/наличия **зарегистрированных** оригиналов, но входной пакет всё равно должен быть полным и соответствовать JSON. Новый UUID требует доступного корня владельца и допустимой длины конечного пути.

Итог содержит Обработано/Принято/Повторов/Ошибок/Сообщения/УдаленоПакетов/ОсталосьПослеПриема. Обработано — число рассмотренных подкаталогов, включая неверные UUID, не число всех элементов Incoming. Ошибка одного кандидата не останавливает цикл. Причины фиксированные безопасные строки по номеру кандидата, без полного пути/исходного JSON/секрета/исключения. Недоступность самого корня/прав/разделения может прекратить импорт до цикла.

## Очистка Incoming после успеха

ОчиститьПринятыйПакет вызывается только после проверки подтверждённого 201 accepted (COMMIT завершён) или 200 duplicate. До чтения пакета сохраняется снимок имён/размеров/UTC-mtime. Недоступные атрибуты, пустое время, время примерно за последние две секунды или из будущего делают снимок ненадёжным: приём возможен, очистка запрещена.

Перед удалением подтверждаются прямой UUID-потомок исходного Incoming, непересечение с оригиналами, точный полный состав обычных файлов, размеры/mtime, JSON и неизменность token/manifest. Затем перед **каждым** удалением снова проверяется весь остаток: оригиналы по одному, document.json последним, потом проверенно пустой каталог. Не удаляются весь Incoming, маска, Documents, посторонние вложения. Хеши или сравнение больших оригиналов не вычисляются; гонку с внешней записью полностью исключить нельзя.

Если очистка не завершилась, приём не откатывается, счётчик ошибок приёма не увеличивается; растут ОсталосьПослеПриема и предупреждение. До удаления ошибка оставляет полный пакет; после частичного удаления может остаться неполный. Автоматической реконструкции источника нет. Полный неизменный пакет при следующем ручном импорте даст duplicate и новую попытку очистки. Ошибка JSON/токена/регистрации, UUID-конфликт или неопределённый COMMIT не дают разрешения на очистку.

## Постоянные оригиналы и сбои

ПодготовитьФайловоеХранилище создаёт собственный .pending с маркером **DoRIS.ServerStorage**: format, operation_id, owner_id, document_id, prepared, manifest. Нет входного токена или пути источника. Это служебный серверный формат, а не новая версия файлового обмена.

ОпубликоватьОригиналы проверяет принадлежность существующего конечного каталога по маркеру/владельцу/UUID/manifest. Полный prepared-набор сверяет по именам/размерам и повторно использует; частичный собственный набор может дополнить отсутствующими файлами новой staging-операции. Каталоги не переименовываются, существующие проверенные файлы не перезаписываются. Неизвестный/неполный маркер, посторонние файлы или несовпадение размеров дают отказ. Произвольный каталог с тем же UUID не объявляется собственным.

ОчиститьСобственныйВременныйКаталог знает конкретный .pending текущего вызова, проверяет имена и убирает только ожидаемые обычные файлы. Конечный каталог не удаляет даже при Rollback/неоднозначном COMMIT. Старые оставшиеся .pending не сканируются автоматически; администратор разбирает их отдельно.

Повторная мобильная выгрузка после серверной очистки создаёт тот же UUID и на сервере становится duplicate при равном манифесте. Отметка Mobile **«Выгружен» означает только завершение записи на стороне телефона**, не доступность сервера и не OCR. Служебные `.incoming-owner-<UUID>.json` текущим импортом не создаются и не читаются, автоматического удаления старых маркеров нет.


## Разделение OCR и записи

Форма сохраняет подготовленную оболочку только в серверной переменной/временном хранилище, не в регистре. Проверяет Document/ТипОбъекта/ТаблицаЗначений/строки до транзакции. В транзакции перечитывает связь/права/версию, вызывает фабрику с Истина, проверяет товары и новую ВерсияДанных. Статус OCR записывается отдельной короткой операцией после фиксации. Оба адреса ВХ очищаются независимо от успеха. Файловые оригиналы в Documents не заменяются результатом OCR.
