# Промежуточная модель OCR

**Проект:** DoRIS
**Версия:** 0.1 beta
**Связанные модули:** `DR_PaddleCloudProvider`, `DR_MistralCloudProvider`, `DR_DocumentProcessor`

---

# 1. Назначение

Промежуточная модель OCR — внутренний унифицированный формат DoRIS для передачи результата распознавания от OCR-провайдера в `DR_DocumentProcessor`.

Она отделяет особенности конкретного OCR API от логики формирования универсальной структуры `Document`.

Общий поток:

```text
OCR API
   │
   ▼
OCR Provider
   │
   │ provider-specific обработка
   ▼
РезультатOCR
   │
   └── МассивДокументов
           ├── СтрокиДокумента
           └── ТаблицыТоваров
   │
   ▼
DR_DocumentProcessor
   │
   ▼
Document
```

Каждый OCR-провайдер может иметь собственный API, формат запроса, формат JSON-ответа и способ представления документа.

После обработки ответа провайдер обязан привести данные к единому контракту DoRIS.

`DR_DocumentProcessor` работает с этим контрактом и не должен зависеть от исходного формата PaddleOCR, Mistral OCR или другого OCR API.

---

# 2. Архитектурная граница

Промежуточная модель OCR является границей между двумя уровнями DoRIS:

```text
           provider-specific
                 │
                 ▼
┌──────────────────────────────────────┐
│           OCR Provider               │
│                                      │
│ HTTP / API / JSON / Markdown / HTML  │
└──────────────────┬───────────────────┘
                   │
                   │ РезультатOCR
                   ▼
════════════════════════════════════════
       ПРОМЕЖУТОЧНАЯ МОДЕЛЬ OCR
════════════════════════════════════════
                   │
                   ▼
┌──────────────────────────────────────┐
│       DR_DocumentProcessor           │
│                                      │
│ нормализация → Document              │
└──────────────────────────────────────┘
```

Все особенности внешнего API должны оставаться выше этой границы.

Ниже нее `DR_DocumentProcessor` должен получать одинаковую структуру независимо от выбранного OCR-провайдера.

---

# 3. Контракт OCR-провайдера

В версии 0.1 beta реализованы два провайдера:

```text
DR_PaddleCloudProvider
DR_MistralCloudProvider
```

Оба предоставляют одинаковую публичную точку выполнения распознавания:

```bsl
ВыполнитьРаспознавание(Настройки, СтруктураФайла)
```

Функция должна вернуть структуру `РезультатOCR`.

Новый OCR-провайдер должен соблюдать тот же контракт.

На уровне `DR_DocumentProcessor` различия между API провайдеров не должны иметь значения.

---

# 4. Структура РезультатOCR

Общая структура:

```text
РезультатOCR
├── JobID
├── ТипОтвета
├── JSONОтвет
├── МассивДокументов
├── Статус
└── Ошибка
```

## В текущих провайдерах она создается внутренней функцией `СоздатьРезультат()`. PaddleOCR и Mistral OCR формируют одинаковый набор полей.

# 5. JobID

`JobID` содержит идентификатор задания внешнего OCR-сервиса, если используемый API работает через механизм заданий.

Для PaddleOCR:

```text
JobID = идентификатор задания PaddleOCR
```

После первоначального POST-запроса PaddleOCR возвращает `jobId`, который используется для последующего получения состояния задания.

Для Mistral OCR отдельное задание в текущей реализации не создается:

```text
JobID = Неопределено
```

Это непосредственно задается при формировании результата Mistral.

Следовательно, `JobID` является частью общего контракта, но его заполнение зависит от возможностей конкретного провайдера.

Новый синхронный OCR-провайдер может возвращать:

```text
JobID = Неопределено
```

---

# 6. ТипОтвета

`ТипОтвета` идентифицирует формат/источник результата OCR.

Значения определяются:

```bsl
DR_Settings.ТипыОтветовOCR()
```

В версии 0.1 beta зарегистрированы:

```text
Unknown    = 0
MistralOCR = 1
PaddleOCR  = 2
AzureOCR   = 3
GoogleOCR  = 4
LocalOCR   = 5
```

Регистрация типа не означает наличие реализованного провайдера.

В версии 0.1 beta фактически подключены:

```text
MistralOCR
PaddleOCR
```

`DR_DocumentProcessor` использует `ТипОтвета` при выборе способа обработки результата. В текущей реализации PaddleOCR и Mistral OCR уже приведены провайдерами к одной промежуточной модели и передаются в общий `РазобратьОтвет()`.

---

# 7. JSONОтвет

`JSONОтвет` содержит исходный итоговый JSON-ответ OCR-провайдера.

Назначение поля:

* сохранение оригинального ответа сервиса;
* диагностика;
* отладка;
* возможность анализа ошибок распознавания;
* возможность повторной проверки поведения преобразования без потери исходного ответа.

`JSONОтвет` не является основной моделью данных DoRIS.

Основная цепочка обработки выглядит так:

```text
JSON провайдера
      │
      ▼
OCR Provider
      │
      ├── JSONОтвет ──────────────► сохраняется
      │
      ▼
МассивДокументов
      │
      ▼
DR_DocumentProcessor
```

`DR_DocumentProcessor` не должен повторно разбирать provider-specific JSON, если провайдер уже сформировал промежуточную модель OCR.

После успешной обработки исходный `JSONОтвет` передается далее вместе с сформированным результатом документа.

---

# 8. Статус

`Статус` показывает общий результат выполнения OCR-провайдера.

Значения определяются:

```bsl
DR_Settings.СтатусыРаспознавания()
```

В версии 0.1 beta:

```text
Успешно = 1
Ошибка  = 0
```

Оба реализованных провайдера используют одинаковое правило:

```text
ТекстОшибки заполнен
        │
        ├── Да  → Ошибка
        │
        └── Нет → Успешно
```

`DR_DocumentProcessor` первым делом проверяет статус.

Если:

```text
РезультатOCR.Статус = Ошибка
```

обработка промежуточной модели не выполняется, а текст ошибки передается в результат Processor.

---

# 9. Ошибка

`Ошибка` содержит текст ошибки OCR-провайдера.

При успешном результате:

```text
Ошибка = ""
```

При неуспешном результате поле должно содержать диагностическое сообщение.

Примеры ошибок, формируемых текущими провайдерами:

```text
Не удалось получить файл из временного хранилища.
Не удалось получить JobID.
Не удалось получить URL результата.
Markdown отсутствует.
```

Провайдер также может передавать ошибку HTTP-уровня или текст исключения.

Поле `Ошибка` относится к результату выполнения OCR-провайдера и не должно использоваться для передачи распознанного содержимого документа.

---

# 10. МассивДокументов

`МассивДокументов` — основная содержательная часть промежуточной модели OCR.

Именно с ней работает `DR_DocumentProcessor`.

Структура:

```text
МассивДокументов
│
├── ДокументOCR [0]
│   ├── СтрокиДокумента
│   └── ТаблицыТоваров
│
├── ДокументOCR [1]
│   ├── СтрокиДокумента
│   └── ТаблицыТоваров
│
└── ...
```

Каждый элемент массива является структурой `ДокументOCR`.

PaddleOCR и Mistral OCR формируют структуры с одинаковыми полями:

```bsl
Документ.Вставить("СтрокиДокумента", СтрокиДокумента);
Документ.Вставить("ТаблицыТоваров", ТаблицыТоваров);
```

---

# 11. ДокументOCR

Один элемент `МассивДокументов` имеет структуру:

```text
ДокументOCR
├── СтрокиДокумента
└── ТаблицыТоваров
```

Эта структура является представлением одного распознанного документа до преобразования в универсальный `Document`.

Не следует путать:

```text
ДокументOCR
```

и:

```text
Document
```

Это разные уровни модели.

```text
ДокументOCR
      │
      │ промежуточные OCR-данные
      ▼
DR_DocumentProcessor
      │
      ▼
Document
      │
      │ универсальная модель DoRIS
      ▼
дальнейшая обработка
```

---

# 12. СтрокиДокумента

`СтрокиДокумента` — массив обычных текстовых строк распознанного документа, не отнесенных провайдером к товарным таблицам.

Тип:

```text
Массив
```

Пример:

```text
СтрокиДокумента
├── "ТОО Компания"
├── "Накладная № 125"
├── "от 15.09.2026"
├── "Поставщик: ..."
└── "Итого: ..."
```

При формировании промежуточной модели текущие провайдеры разбирают полученный Markdown построчно.

Пустые строки пропускаются.

Если строка является HTML-таблицей, она передается в обработку таблиц.

Все остальные строки добавляются в `СтрокиДокумента`.
В версии 0.1 beta `DR_DocumentProcessor` сохраняет этот массив:

```bsl
Документ.МассивСтрок = ДокументOCR.СтрокиДокумента;
```

Дальнейший разбор реквизитов по `СтрокиДокумента` в основном рабочем pipeline версии 0.1 beta пока не выполняется.

В модуле присутствует код для будущей обработки типа и реквизитов документа, который предполагается использовать при дальнейшем развитии проекта.

---

# 13. ТаблицыТоваров

`ТаблицыТоваров` содержит распознанные табличные данные документа.

Структура:

```text
ТаблицыТоваров
│
├── Таблица [0]
│   ├── Строка [0]
│   │   ├── Ячейка [0]
│   │   ├── Ячейка [1]
│   │   └── ...
│   │
│   ├── Строка [1]
│   └── ...
│
├── Таблица [1]
└── ...
```

Таким образом используются три вложенных уровня массивов:

```text
Массив таблиц
    ↓
Массив строк таблицы
    ↓
Массив значений ячеек
```

Пример:

```text
ТаблицыТоваров[0] =

[
    ["№", "Код", "Товар", "Количество", "Цена", "Сумма"],
    ["1", "00001", "Товар A", "10 шт", "500", "5000"],
    ["2", "00002", "Товар B", "5 шт", "700", "3500"]
]
```

На этом уровне данные еще являются OCR-данными.

Физическое количество ячеек строки может отличаться от логического количества колонок документа.

Нормализация таких различий является ответственностью `DR_DocumentProcessor` и подробно описана в `TABLE_PROCESSING.md`.

---

# 14. Заголовок первой таблицы

Текущий контракт между провайдерами и `DR_DocumentProcessor` имеет важное практическое условие:

**первая строка первой таблицы должна содержать заголовки колонок.**

`DR_DocumentProcessor` использует:

```text
ДокументOCR.ТаблицыТоваров[0][0]
```

как источник схемы колонок.

Пример:

```text
Таблица [0]

[0] ["№", "Товар", "Количество", "Цена"]
[1] ["1", "Товар A", "10 шт", "500"]
[2] ["2", "Товар B", "5 шт", "700"]
```

Здесь:

```text
[0] = заголовок
[1...] = данные
```

Это является частью фактического контракта версии 0.1 beta.

---

# 15. Последующие таблицы

В одном `ДокументOCR` может находиться несколько таблиц.

Первая таблица используется для построения схемы.

Последующие таблицы рассматриваются `DR_DocumentProcessor` как продолжение товарной таблицы и обрабатываются без ожидания новой строки заголовка.

```text
Таблица [0]
    ↓
заголовок + данные

Таблица [1]
    ↓
данные

Таблица [2]
    ↓
данные
```

`DR_DocumentProcessor` устанавливает наличие заголовка только для таблицы с индексом `0`.

Следовательно, провайдер должен учитывать это при формировании `ТаблицыТоваров`.

---

# 16. Представление ячеек

Значение каждой OCR-ячейки передается как текстовое значение.

На уровне промежуточной модели провайдер не обязан приводить:

```text
Количество
Цена
Сумма
НДС
```

к типам платформы 1С.

Например:

```text
"10"
"1 000,50"
"10 шт"
"12%"
```

являются допустимыми OCR-значениями.

Разделение некоторых объединенных значений и преобразование необходимых полей выполняется далее в `DR_DocumentProcessor`.

Это позволяет не переносить бизнес-логику `Document` внутрь OCR-провайдера.

---

# 17. Физические и логические колонки

На уровне промежуточной модели таблица сохраняет **физическое представление**, полученное после разбора результата OCR.

Например, визуально документ содержит:

```text
| Товар | Количество | Цена |
```

Провайдер может сформировать строку:

```text
["Товар A", "10 шт", "500"]
```

или:

```text
["Товар A", "10", "шт", "500"]
```

Провайдеру не требуется самостоятельно приводить эти два варианта к одной логической схеме.

Это задача `DR_DocumentProcessor`.

Разделение ответственности:

```text
OCR Provider
     │
     │ извлекает физические таблицы
     ▼
ТаблицыТоваров
     │
     │ физические OCR-ячейки
     ▼
DR_DocumentProcessor
     │
     │ логическая нормализация
     ▼
Document.ТабличнаяЧасть
```

Алгоритм нормализации описан в `TABLE_PROCESSING.md`.

# 18. Формирование модели PaddleOCR

PaddleOCR возвращает собственный JSON.

Провайдер извлекает из:

```text
result.layoutParsingResults[].markdown.text
```

Markdown отдельных результатов разбора и объединяет его в общий Markdown.

Далее:

```text
Paddle JSON
     ↓
ПолучитьРезультатPaddle()
     ↓
Markdown
     ↓
РазобратьMarkdownPaddle()
     ↓
СтрокиДокумента
+
ТаблицыТоваров
     ↓
МассивДокументов
```

HTML-таблицы разбираются через DOM.

Каждый `<tr>` становится строкой массива, каждый `<td>` — источником значения физической ячейки.

После этого provider-specific структура PaddleOCR больше не используется `DR_DocumentProcessor`.

---

# 19. Формирование модели Mistral OCR

Mistral OCR также сначала преобразуется в Markdown-представление.

Из массива `pages` извлекается:

```text
page.markdown
```

а содержимое таблицы берется из:

```text
page.tables[0].content
```

В текущей версии обрабатывается простой вариант — одна таблица на странице.

Далее:

```text
Mistral JSON
     ↓
ПолучитьРезультатMistralOCR()
     ↓
Markdown
     ↓
РазобратьMarkdownMistralOCR()
     ↓
СтрокиДокумента
+
ТаблицыТоваров
     ↓
МассивДокументов
```

HTML-таблица разбирается через DOM. При отсутствии `<td>` Mistral-провайдер также проверяет `<th>`.

На выходе получается тот же контракт, что и у PaddleOCR.

---

# 20. Почему Markdown не входит в РезультатOCR

Markdown используется текущими провайдерами как внутренний промежуточный формат при преобразовании ответа OCR API.

Но он не входит в унифицированный контракт `РезультатOCR`.

Фактическая цепочка:

```text
API JSON
   ↓
Markdown
   ↓
СтрокиДокумента + ТаблицыТоваров
   ↓
МассивДокументов
   ↓
РезультатOCR
```

Таким образом Markdown является деталью реализации конкретного провайдера.

Новый OCR-провайдер не обязан использовать Markdown вообще.

Если API нового провайдера позволяет сразу сформировать:

```text
СтрокиДокумента
ТаблицыТоваров
```

он может сделать это непосредственно из своего JSON.

Это один из основных принципов промежуточной модели OCR.

---

# 21. Почему JSONОтвет сохраняется, а Markdown — нет

`JSONОтвет` является оригинальным ответом внешнего сервиса и полезен для диагностики поведения API.

Markdown в текущей реализации является уже производным представлением, используемым провайдером для построения унифицированной структуры.

Поэтому контракт разделяет их следующим образом:

```text
JSONОтвет
    │
    └── сохраняется как исходный ответ API

Markdown
    │
    └── внутренняя деталь преобразования провайдера

МассивДокументов
    │
    └── унифицированные данные для ядра DoRIS
```

---

# 22. Ошибка формирования промежуточной модели

Успешный HTTP-запрос сам по себе не означает успешного результата OCR.

Например, если провайдер получил корректный HTTP-ответ, но не смог извлечь Markdown, он формирует ошибочный `РезультатOCR`.

Текущие PaddleOCR и Mistral OCR используют сообщение:

```text
Markdown отсутствует.
```

Следовательно, ответственность провайдера заканчивается только после того, как provider-specific ответ успешно преобразован в промежуточную модель OCR.

---

# 23. Проверка модели в DR_DocumentProcessor

`DR_DocumentProcessor` получает `РезультатOCR` через:

```bsl
Обработать(РезультатOCR)
```

Сначала выполняется проверка типа входного значения.

После этого проверяется `Статус`.

Затем проверяется `ТипОтвета`.

При разборе результата дополнительно проверяется:

```text
МассивДокументов <> Неопределено
```

и:

```text
ТипЗнч(МассивДокументов) = Тип("Массив")
```

Таким образом `МассивДокументов` является обязательной частью успешного результата, предназначенного для дальнейшей обработки.

---

# 24. Минимальный успешный результат провайдера

Концептуально минимальный успешный `РезультатOCR` имеет вид:

```text
РезультатOCR
│
├── JobID = Неопределено
├── ТипОтвета = <тип нового провайдера>
├── JSONОтвет = "<исходный JSON>"
├── МассивДокументов
│   └── ДокументOCR
│       ├── СтрокиДокумента = []
│       └── ТаблицыТоваров = [...]
├── Статус = Успешно
└── Ошибка = ""
```

`JobID` может отсутствовать как содержательное значение, если внешний API его не использует.

`СтрокиДокумента` может быть пустым массивом.

`ТаблицыТоваров` может быть пустым массивом, если таблицы не распознаны.

Но сама структура `ДокументOCR` должна соответствовать контракту, ожидаемому `DR_DocumentProcessor`.

---

# 25. Ошибочный результат провайдера

При ошибке провайдер должен вернуть тот же верхнеуровневый контракт:

```text
РезультатOCR
│
├── JobID
├── ТипОтвета
├── JSONОтвет
├── МассивДокументов
├── Статус = Ошибка
└── Ошибка = "<описание ошибки>"
```

Это позволяет `DR_RecognitionService` и `DR_DocumentProcessor` обрабатывать ошибки разных провайдеров одинаковым способом.

Провайдер не должен возвращать совершенно другой тип значения только потому, что запрос завершился ошибкой.

---

# 26. Требования к новому OCR-провайдеру

При добавлении нового провайдера разработчик должен реализовать преобразование:

```text
ответ нового OCR API
        ↓
provider-specific parsing
        ↓
РезультатOCR
        ↓
МассивДокументов
        ↓
ДокументOCR
        ├── СтрокиДокумента
        └── ТаблицыТоваров
```

Провайдер должен:

1. реализовать `ВыполнитьРаспознавание()`;
2. сформировать `РезультатOCR`;
3. установить корректный `ТипОтвета`;
4. сохранить исходный итоговый ответ в `JSONОтвет`;
5. сформировать `МассивДокументов`;
6. отделить обычные строки документа от таблиц;
7. представить таблицы массивами строк и физических ячеек;
8. установить `Статус`;
9. заполнить `Ошибка` при неуспешном выполнении.

Провайдер не должен:

* создавать `Document`;
* заполнять объект документа 1С;
* знать структуру конкретной конфигурации 1С;
* выполнять сопоставление номенклатуры;
* преобразовывать товарную таблицу в `ТаблицаЗначений`;
* реализовывать логическую нормализацию физических колонок;
* переносить provider-specific JSON-разбор в `DR_DocumentProcessor`.

---

# 27. Регистрация нового типа ответа

Для нового провайдера должен существовать уникальный тип ответа в:

```bsl
DR_Settings.ТипыОтветовOCR()
```

После этого провайдер должен устанавливать:

```text
РезультатOCR.ТипОтвета
```

в соответствующее значение.

В версии 0.1 beta `DR_DocumentProcessor` явно принимает только:

```text
PaddleOCR
MistralOCR
```

Остальные значения приводят к:

```text
Неизвестный тип OCR-провайдера.
```

Поэтому одной регистрации значения в `ТипыОтветовOCR()` недостаточно: при фактическом подключении нового провайдера необходимо также включить его в поддерживаемый поток обработки.

---

# 28. Требования к ТаблицыТоваров нового провайдера

Для совместимости с текущим `DR_DocumentProcessor` новый провайдер должен соблюдать следующие правила.

Первая таблица должна содержать строку заголовков:

```text
ТаблицыТоваров[0][0]
```

Последующие строки первой таблицы должны содержать данные.

Последующие элементы `ТаблицыТоваров` рассматриваются как продолжение товарной таблицы без обязательного повторного заголовка.

Каждая строка должна быть массивом физических значений:

```text
["1", "Товар A", "10 шт", "500"]
```

Провайдер не обязан самостоятельно разделять:

```text
"10 шт"
```

на:

```text
"10"
"шт"
```

если физический OCR-результат содержит их в одной ячейке.

Это выполняет `DR_DocumentProcessor`.

# 29. Пример промежуточной модели

Пример успешного результата:

```text
РезультатOCR

JobID:
    "abc123"

ТипОтвета:
    PaddleOCR

JSONОтвет:
    "{ ... исходный JSON ... }"

Статус:
    Успешно

Ошибка:
    ""

МассивДокументов:
    [
        {
            СтрокиДокумента:
            [
                "ТОО Поставщик",
                "Накладная № 125 от 15.09.2026"
            ],

            ТаблицыТоваров:
            [
                [
                    ["№", "Код", "Товар", "Количество", "Цена", "Сумма"],
                    ["1", "00001", "Товар A", "10 шт", "500", "5000"],

                ]
            ]
        }
    ]
```

После передачи в `DR_DocumentProcessor` эта структура преобразуется в `Document`.

# 31. Основной инвариант модели

Основное архитектурное требование промежуточной модели OCR:

> `DR_DocumentProcessor` должен получать одинаковую структуру OCR-данных независимо от того, какой внешний OCR-провайдер использовался для распознавания документа.

Из этого следует второе требование:

> Особенности JSON, HTTP API, Markdown и других форматов конкретного OCR-сервиса должны обрабатываться внутри соответствующего OCR-провайдера и не должны распространяться в ядро DoRIS.

Именно соблюдение этого контракта позволяет подключать новые OCR-провайдеры без переноса их специфики в логику формирования `Document`.

---

# 32. Стабильность контракта в версии 0.1 beta

На этапе 0.1 beta промежуточная модель является внутренним контрактом DoRIS и может развиваться вместе с проектом.

При ее изменении необходимо учитывать как минимум три стороны:

```text
OCR Provider
      ↓
РезультатOCR / МассивДокументов
      ↓
DR_DocumentProcessor
```

Изменение структуры только на стороне одного провайдера без соответствующего изменения общего контракта недопустимо.

Если новый OCR-провайдер требует дополнительных provider-specific данных, предпочтительно обрабатывать их внутри самого провайдера и передавать в ядро уже нормализованный результат.

Расширять общий контракт следует только тогда, когда новые данные имеют смысл для ядра DoRIS независимо от конкретного OCR-сервиса.
