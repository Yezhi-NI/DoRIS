# Pipeline обработки документа DoRIS

**Проект:** DoRIS
**Версия:** 0.1 beta

---

# 1. Назначение

Этот документ описывает полный поток обработки файла в DoRIS: от передачи файла клиентом 1С до получения нормализованной структуры `Document` и, при соответствующем сценарии, заполнения документа конкретной конфигурации 1С.

Основной pipeline:

```text
Клиент 1С
   │
   ▼
DR_RecognitionService
   │
   ├── DR_Validation
   │
   └── DR_Settings
          │
          ▼
     OCR Provider
     ├── DR_PaddleCloudProvider
     └── DR_MistralCloudProvider
          │
          ▼
     DR_HttpClient
          │
          ▼
      OCR API
          │
          ▼
     ответ провайдера
          │
          ▼
     OCR Provider
          │
          ▼
      РезультатOCR
          │
          ▼
  DR_DocumentProcessor
          │
          ▼
       Document
          │
          ├── возврат результата
          │
          └── DR_DocumentFactory
                  │
                  ▼
        объект конкретной
        конфигурации 1С
```

---

# 2. Уровни обработки

Pipeline разделен на несколько независимых уровней.

```text
┌──────────────────────────────────────────────┐
│ 1. Клиентский уровень                        │
│    подготовка файлов и вызов DoRIS           │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│ 2. Service layer                             │
│    DR_RecognitionService                     │
│    координация всего процесса                │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│ 3. Provider layer                            │
│    PaddleOCR / Mistral OCR                   │
│    взаимодействие с конкретным OCR API       │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│ 4. Transport layer                           │
│    DR_HttpClient                             │
│    HTTP/HTTPS                                │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│ 5. OCR model                                 │
│    РезультатOCR → МассивДокументов           │
│    промежуточная модель OCR                  │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│ 6. Processing layer                          │
│    DR_DocumentProcessor                      │
│    нормализация OCR                          │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│ 7. Document model                            │
│    универсальная структура Document          │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│ 8. Integration layer                         │
│    DR_DocumentFactory                        │
│    заполнение объекта конкретной             │
│    конфигурации 1С                           │
└──────────────────────────────────────────────┘
```

Не каждый вызов проходит последний уровень. Полученный `Document` может использоваться клиентом непосредственно.

---

# 3. Точка входа

Основной публичный вызов библиотеки:

```bsl
DR_RecognitionService.РаспознатьМассивФайлов(
    МассивФайловДляРаспознавания
)
```

`DR_RecognitionService` является координатором pipeline.

Он не выполняет самостоятельно:

```text
HTTP-запросы
разбор provider-specific JSON
разбор OCR-таблиц
нормализацию таблиц
```

Эти задачи передаются специализированным модулям.

---

# 4. Входной массив

`РаспознатьМассивФайлов()` получает массив структур распознавания.

Каждый элемент массива соответствует одному обрабатываемому файлу.

В текущем pipeline сервис использует как минимум:

```text
СтруктураРаспознавания
├── ФайлРаспознавания
└── ОбъектЗаполнения
```

`ФайлРаспознавания` передается OCR-провайдеру.

Внутри него провайдер использует:

```text
АдресФайла
ТипФайла
```

`ОбъектЗаполнения` используется только в сценарии заполнения существующего объекта конкретной конфигурации 1С.

---

# 5. Проверка входного параметра

Первое действие `DR_RecognitionService`:

```text
МассивФайловДляРаспознавания
          │
          ▼
DR_Validation.ПроверитьТипМассив()
```

Таким образом проверка типа публичного входного параметра выполняется до начала распознавания.

`DR_Validation` является общим механизмом проверки параметров библиотеки.

---

# 6. Получение настроек

После проверки входного массива вызывается:

```bsl
DR_Settings.ПолучитьНастройки()
```

`DR_Settings` определяет активного OCR-провайдера и получает его настройки.

Концептуально:

```text
активный провайдер
        │
        ▼
DR_Settings
        │
        ├── параметры подключения
        ├── API key
        ├── prompt
        └── OCR Provider
```

В `Настройки.ПровайдерOCR` передается не строковое имя, а соответствующий общий модуль провайдера.

Для текущей версии возможны:

```text
MistralOCR → DR_MistralCloudProvider
PaddleOCR  → DR_PaddleCloudProvider
```

---

# 7. Обработка массива файлов

После получения настроек сервис создает:

```bsl
Результаты = Новый Массив;
```

и последовательно обрабатывает каждый элемент входного массива:

```text
МассивФайлов
     │
     ├── Файл 1 → РаспознатьФайл()
     ├── Файл 2 → РаспознатьФайл()
     ├── ...
     └── Файл N → РаспознатьФайл()
```

Каждый файл проходит собственный OCR pipeline.

Результат каждого вызова добавляется в общий массив `Результаты`.

---

# 8. Передача файла провайдеру

Внутренняя функция:

```bsl
РаспознатьФайл(
    Провайдер,
    Настройки,
    СтруктураРаспознавания
)
```

вызывает единый контракт OCR-провайдера:

```bsl
Провайдер.ВыполнитьРаспознавание(
    Настройки,
    СтруктураРаспознавания.ФайлРаспознавания
)
```

Это ключевая точка расширения provider layer.

`DR_RecognitionService` не должен знать, каким образом конкретный OCR API принимает файл и получает результат.

---

# 9. Контракт OCR-провайдера

Каждый OCR-провайдер должен реализовать:

```bsl
ВыполнитьРаспознавание(
    Настройки,
    СтруктураФайла
)
```

и вернуть унифицированный:

```text
РезультатOCR
├── JobID
├── ТипОтвета
├── JSONОтвет
├── МассивДокументов
├── Статус
└── Ошибка
```

Таким образом provider-specific pipeline заканчивается созданием общего `РезультатOCR`.

После этой точки `DR_DocumentProcessor` не должен зависеть от исходного API-формата провайдера.

Подробный контракт описан в `OCR_MODEL.md`.

---

# 10. Получение файла провайдером

Оба текущих провайдера получают файл из временного хранилища:

```text
СтруктураФайла.АдресФайла
          │
          ▼
ПолучитьИзВременногоХранилища()
          │
          ▼
ДвоичныеДанные
```

После получения данных исходный адрес удаляется из временного хранилища.

Далее способы отправки различаются.

---

# 11. Pipeline PaddleOCR

Для PaddleOCR используется асинхронная схема.

```text
ДвоичныеДанные
      │
      ▼
формирование параметров
и заголовков PaddleOCR
      │
      ▼
DR_HttpClient
      │
      ▼
POST PaddleOCR API
      │
      ▼
JobID
      │
      ▼
опрос состояния задания
      │
      ├── processing → повторный GET
      │
      ├── failed     → ошибка
      │
      └── done
           │
           ▼
       resultUrl
           │
           ▼
          GET
           │
           ▼
      итоговый JSON
```

После получения итогового JSON провайдер извлекает Markdown и преобразует его в промежуточную модель OCR.

---

# 12. Pipeline Mistral OCR

Mistral OCR использует другой транспортный сценарий.

Файл преобразуется в Base64:

```text
ДвоичныеДанные
      │
      ▼
Base64
      │
      ▼
data URL
```

Для PDF формируется:

```text
data:application/pdf;base64,...
```

Для изображения текущая реализация формирует:

```text
data:image/jpeg;base64,...
```

После этого:

```text
JSON request
     │
     ▼
DR_HttpClient
     │
     ▼
POST Mistral OCR
     │
     ▼
JSON response
```

В отличие от PaddleOCR отдельный `JobID` и цикл polling здесь не используются.

---

# 13. Роль DR_HttpClient

Оба провайдера используют общий транспортный слой:

```text
OCR Provider
     │
     ▼
DR_HttpClient
     │
     ▼
HTTP/HTTPS
```

`DR_HttpClient` отвечает за:

```text
HTTPСоединение
HTTPЗапрос
HTTPS / OpenSSL
GET
POST
JSON body
multipart/form-data
HTTP response
HTTP error
```

Провайдер при этом сам определяет:

```text
URL
заголовки
параметры
формат тела
тип файла
```

То есть граница ответственности выглядит так:

```text
Provider
    │
    ├── знает протокол конкретного OCR API
    │
    ▼
HttpClient
    │
    ├── знает только HTTP
    │
    ▼
Internet
```

---

# 14. HTTP-результат

`DR_HttpClient` возвращает унифицированную структуру:

```text
HTTPРезультат
├── КодСостояния
├── Тело
├── Заголовки
└── Ошибка
```

Успешным считается HTTP-код:

```text
200 <= КодСостояния < 300
```

Проверка выполняется:

```bsl
DR_HttpClient.ПроверитьHTTPОтвет()
```

После этого дальнейшую интерпретацию тела ответа выполняет OCR-провайдер.

---

# 15. Provider-specific JSON

Полученный HTTP JSON еще не является данными, с которыми должен работать `DR_DocumentProcessor`.

Каждый провайдер самостоятельно разбирает свой формат.

```text
Paddle JSON                    Mistral JSON
    │                              │
    ▼                              ▼
DR_PaddleCloudProvider       DR_MistralCloudProvider
    │                              │
    └──────────────┬───────────────┘
                   ▼
          промежуточная модель OCR
```

Это позволяет изолировать различия внешних API внутри provider layer.

---

# 16. Формирование промежуточной модели OCR

В текущей реализации оба провайдера получают из ответа текстовое представление документа и разделяют его на:

```text
ДокументOCR
├── СтрокиДокумента
└── ТаблицыТоваров
```

`СтрокиДокумента` содержит обычные строки документа.

`ТаблицыТоваров` содержит таблицы в форме вложенных массивов физических ячеек.

Полученные `ДокументOCR` помещаются в:

```text
РезультатOCR.МассивДокументов
```

Таким образом обязательная граница provider layer:

```text
provider-specific response
          │
          ▼
унифицированный РезультатOCR
          │
          └── МассивДокументов
```

Новый OCR-провайдер должен сформировать такую же промежуточную модель.

---

# 17. Передача результата в Processor

После завершения OCR сервис получает:

```text
РезультатOCR
```

и передает его:

```bsl
DR_DocumentProcessor.Обработать(РезультатOCR)
```

С этого момента provider layer завершен.

---

# 18. Начало работы DR_DocumentProcessor

`DR_DocumentProcessor` сначала проверяет тип входного значения.

Затем проверяется:

```text
РезультатOCR.Статус
```

Если OCR-провайдер вернул ошибку:

```text
Статус = Ошибка
```

Processor формирует результат ошибки и дальнейшая обработка документа не выполняется.

---

# 19. Определение типа OCR-ответа

Processor проверяет:

```text
РезультатOCR.ТипОтвета
```

В текущей версии поддерживаются:

```text
PaddleOCR
MistralOCR
```

Оба текущих провайдера уже приводят свои данные к одной промежуточной модели, поэтому далее используется общий:

```bsl
РазобратьОтвет(РезультатOCR)
```

Если тип OCR неизвестен, возвращается ошибка:

```text
Неизвестный тип OCR-провайдера.
```

---

# 20. Создание Document

Processor создает базовую структуру:

```bsl
DR_DocumentFactory.СоздатьСтруктуруДокумент()
```

Результат:

```text
Document
├── ТипОбъекта
├── ТипДокумента
├── МассивСтрок
├── РеквизитыДокумента
└── ТабличнаяЧасть
```

Подробное описание структуры находится в `DOCUMENT.md`.

---

# 21. Обработка МассивДокументов

Processor перебирает:

```text
РезультатOCR.МассивДокументов
```

Для каждого:

```text
ДокументOCR
```

выполняется:

```text
ДокументOCR.СтрокиДокумента
          │
          ▼
Document.МассивСтрок
```

Если `ТаблицыТоваров` присутствуют, документ передается в:

```bsl
РазобратьДокументOCR()
```

---

# 22. Текущая обработка Document

В версии 0.1 beta `РазобратьДокументOCR()` выполняет прежде всего обработку товарной таблицы.

```text
ДокументOCR
     │
     ▼
ТипОбъекта = "Документ"
     │
     ▼
РазобратьТаблицыТоваров()
     │
     ▼
ЗаполнитьТабличнуюЧасть()
     │
     ▼
Document
```

Логика распознавания реквизитов шапки подготовлена в модуле, но в текущий основной pipeline еще не включена.

---

# 23. Pipeline обработки таблиц

Обработка таблиц является наиболее сложной частью `DR_DocumentProcessor`.

Упрощенно:

```text
ДокументOCR.ТаблицыТоваров
          │
          ▼
СоздатьСхемуКолонок()
          │
          ▼
логическая схема таблицы
          │
          ▼
для каждой физической таблицы
          │
          ▼
ОпределитьВариантСхемыТаблицы()
          │
          ├── ЛогическаяСхема
          ├── ОбъединеннаяСхема
          └── НесовместимаяСхема
          │
          ▼
РазобратьСтрокуПоСхеме()
          │
          ▼
массив нормализованных строк
          │
          ▼
СоздатьТаблицуТоваров()
          │
          ▼
ТаблицаЗначений
          │
          ▼
ЗаполнитьТабличнуюЧасть()
          │
          ▼
Document.ТабличнаяЧасть
```

Полный алгоритм физических и логических колонок описан отдельно в `TABLE_PROCESSING.md`.

---

# 24. Схема колонок

Схема строится по первой OCR-таблице.

Первая строка первой таблицы рассматривается как заголовок:

```text
ТаблицыТоваров[0][0]
```

Из него создается логическая:

```text
СхемаКолонок
```

Схема используется затем для обработки остальных строк и продолжений таблицы.

Это позволяет отделить:

```text
физические OCR-ячейки
```

от:

```text
логических колонок документа
```

---

# 25. Продолжение таблицы

Первая таблица считается содержащей заголовок:

```text
ЕстьЗаголовок = Истина
```

Для последующих таблиц:

```text
ЕстьЗаголовок = Ложь
```

Поэтому первая строка первой таблицы пропускается как заголовок, а строки последующих таблиц рассматриваются как продолжение данных.

Это используется для обработки таблиц, разделенных OCR на несколько частей или страниц.

---

# 26. Расширяемые колонки

В текущей версии специальное правило существует для:

```text
Количество
```

Значение вида:

```text
800 шт
```

может логически представлять:

```text
Количество = 800
Единица измерения = шт
```

Поэтому Processor способен расширить одну физическую OCR-ячейку в две логические колонки.

Именно для этого в алгоритме существуют понятия:

```text
физическая колонка
логическая колонка
расширяемая колонка
объединенная схема
```

Подробности находятся в `TABLE_PROCESSING.md`.

---

# 27. Создание ТаблицаЗначений

После нормализации строк Processor создает стандартную:

```bsl
ТаблицаЗначений
```

Известные OCR-заголовки сопоставляются с полями модели через:

```bsl
DR_DocumentFactory.СоответствиеКолонок()
```

Неизвестные колонки не удаляются.

Для них создаются технические имена:

```text
Колонка1
Колонка2
...
```

с сохранением исходного заголовка OCR.

---

# 28. Заполнение Document.ТабличнаяЧасть

Полученная промежуточная `ТаблицаЗначений` переносится в:

```text
Document.ТабличнаяЧасть
```

При этом числовые значения преобразуются из строк.

В текущей реализации это относится прежде всего к:

```text
Количество
Цена
Сумма
СуммаНДС
СуммаБезНДС
```

Если некоторые числовые значения отсутствуют, для них устанавливается `0`.

---

# 29. Результат Processor

После обработки создается:

```text
РезультатDocumentProcessor
├── Document
├── Markdown
├── JSON
└── Ошибка
```

Основной полезный результат:

```text
Document
```

`JSON` содержит исходный итоговый JSON OCR-провайдера и может использоваться для диагностики.

В текущей реализации:

```text
Markdown = ""
```

---

# 30. Возврат в DR_RecognitionService

Processor возвращает результат сервису:

```text
DR_DocumentProcessor
        │
        ▼
РезультатDocumentProcessor
        │
        ▼
DR_RecognitionService
```

Если:

```text
РезультатDocumentProcessor.Ошибка
```

заполнена, сервис сразу возвращает этот результат для текущего файла.

---

# 31. Два сценария после формирования Document

После успешного Processor pipeline разделяется.

```text
                  Document
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
 только результат        заполнение объекта
 распознавания                 1С
          │                     │
          │             DR_DocumentFactory
          │                     │
          └──────────┬──────────┘
                     ▼
                 результат
```

Выбор зависит от настроек и наличия `ОбъектЗаполнения`.

---

# 32. Сценарий без создания документа 1С

Если требуется только результат распознавания, сервис возвращает результат Processor.

Это позволяет использовать DoRIS как библиотеку:

```text
файл
 │
 ▼
OCR
 │
 ▼
Document
 │
 ▼
клиентский код
```

без обязательного создания объекта конкретной конфигурации.

---

# 33. Сценарий заполнения документа 1С

Если передан `ОбъектЗаполнения` и выбран соответствующий режим, сервис вызывает:

```bsl
DR_DocumentFactory.СоздатьДокумент(
    РезультатDocumentProcessor,
    ОбъектЗаполнения
)
```

Далее:

```text
Document
    │
    ▼
DR_DocumentFactory
    │
    ▼
ПолучитьОбъект()
    │
    ▼
заполнение Товары
    │
    ▼
поиск Номенклатуры
    │
    ▼
расчет НДС
    │
    ▼
заполнение счетов учета
    │
    ▼
запись документа
```

Эта часть зависит от конкретной конфигурации 1С и не относится к универсальному ядру модели `Document`.

# 34. Формирование общего массива результатов

Результат обработки каждого входного файла добавляется в:

```text
Результаты
```

Таким образом:

```text
Файл 1 → Результат 1
Файл 2 → Результат 2
...
Файл N → Результат N
```

Ошибка одного файла представляется результатом этого файла и не меняет сам принцип формирования общего массива.

# 35. Возврат результата клиенту

После обработки всех файлов массив:

```text
Результаты
```

помещается во временное хранилище:

```bsl
ПоместитьВоВременноеХранилище(Результаты)
```

Публичная функция возвращает:

```text
АдресХранилищаРезультаты
```

Следовательно, фактический публичный pipeline версии 0.1 beta заканчивается так:

```text
Массив результатов
       │
       ▼
временное хранилище 1С
       │
       ▼
адрес временного хранилища
       │
       ▼
клиент
```

Клиент получает сам массив результатов из временного хранилища.

# 38. Основные структуры данных pipeline

Через pipeline проходят четыре принципиально разных уровня данных.

```text
1. СтруктураФайла
       │
       ▼
2. provider-specific JSON
       │
       ▼
3. РезультатOCR / ДокументOCR
       │
       ▼
4. Document
```

Их нельзя смешивать.

### СтруктураФайла

Описывает передаваемый на распознавание файл.

### Provider-specific JSON

Исходный ответ PaddleOCR или Mistral OCR.

### РезультатOCR

Унифицированный контракт между OCR-провайдером и `DR_DocumentProcessor`.

### Document

Универсальная нормализованная модель распознанного документа.

# 39. Главная архитектурная граница

Ключевая граница DoRIS проходит здесь:

```text
┌──────────────────────────────┐
│ provider-specific            │
│                              │
│ PaddleOCR JSON               │
│ Mistral OCR JSON             │
└──────────────┬───────────────┘
               │
               ▼
════════════════════════════════
       РезультатOCR
       МассивДокументов
════════════════════════════════
               │
               ▼
┌──────────────────────────────┐
│ provider-independent         │
│                              │
│ DR_DocumentProcessor         │
│ Document                     │
└──────────────────────────────┘
```

Новый OCR-провайдер должен привести свой ответ к установленной промежуточной модели.

За этой границей алгоритмы обработки документа не должны знать формат внешнего API.

# 40. Распределение ответственности

```text
DR_RecognitionService
    координация pipeline

DR_Settings
    настройки и выбор провайдера

DR_Validation
    проверка входных параметров

DR_HttpClient
    HTTP transport

DR_PaddleCloudProvider
    протокол и ответ PaddleOCR

DR_MistralCloudProvider
    протокол и ответ Mistral OCR

DR_DocumentProcessor
    OCR model → Document
    нормализация таблиц

DR_DocumentFactory
    структура Document
    интеграция с объектом конкретной конфигурации 1С
```

# 41. Правило добавления нового OCR-провайдера

Новый провайдер должен встроиться в существующий участок:

```text
                   ┌── PaddleOCR
                   │
RecognitionService ├── Mistral OCR
                   │
                   └── НовыйProvider
                          │
                          ▼
                    РезультатOCR
                          │
                          ▼
                  DocumentProcessor
```

Провайдер обязан:

1. принять `Настройки` и `СтруктураФайла`;
2. самостоятельно взаимодействовать со своим API;
3. разобрать provider-specific ответ;
4. сформировать промежуточную OCR-модель;
5. вернуть стандартный `РезультатOCR`.

Изменение алгоритма `DR_DocumentProcessor` только из-за другого формата внешнего OCR API не является предполагаемым способом подключения нового провайдера.

# 42. Обработка ошибок

Ошибки могут возникнуть на нескольких уровнях:

```text
Validation
    │
    ▼
Settings
    │
    ▼
HTTP
    │
    ▼
OCR Provider
    │
    ▼
DocumentProcessor
    │
    ▼
DocumentFactory
```

Транспортный слой возвращает ошибку в структуре HTTP-результата.

Провайдер преобразует ошибку в:

```text
РезультатOCR.Статус = Ошибка
РезультатOCR.Ошибка = <текст>
```

Processor преобразует ошибку OCR или собственную ошибку в свой стандартный результат:

```text
Document = Неопределено
Ошибка   = <текст>
```

Сервис добавляет полученный результат в общий массив результатов.

# 43. Инварианты pipeline

При развитии DoRIS необходимо сохранять следующие правила.

**Service layer не разбирает OCR.**

```text
DR_RecognitionService
```

только координирует процесс.

**HttpClient не знает OCR-провайдеров.**

```text
DR_HttpClient
```

работает только с HTTP.

**Провайдер знает внешний API, но не формирует Document.**

```text
OCR Provider
    ↓
РезультатOCR
```

**Processor не должен зависеть от внешнего JSON.**

```text
РезультатOCR
    ↓
DR_DocumentProcessor
    ↓
Document
```

**Document не должен зависеть от конкретного OCR-провайдера.**

**Заполнение объекта конкретной конфигурации 1С является отдельным интеграционным уровнем.**
